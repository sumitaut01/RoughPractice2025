Page Object Model vs Page Factory

Interview-ready study guide — concept, distinction, and driver internals

The Core Distinction

Page Object Model (POM) Design Pattern

  • A concept, not a library
  • Rule: one class per web page/screen
  • Elements + actions encapsulated inside the class
  • Tests call methods, never touch locators directly
  • Can be implemented with plain driver.findElement() — no special tooling required

PageFactory Selenium Utility

  • A concrete class: org.openqa.selenium.support.PageFactory
  • One specific way to implement POM
  • Uses @FindBy annotations instead of manual findElement() calls
  • Adds reflection + dynamic proxies under the hood
  • Considered semi-legacy in modern frameworks
The one-line answer that lands: POM is the "what/why" — the architecture rule. PageFactory is "one tool that helps you write it faster." You can do POM without PageFactory at all.

Minimal Example

public class LoginPage {

    @FindBy(id = "username")
    WebElement usernameField;

    @FindBy(id = "password")
    WebElement passwordField;

    public LoginPage(WebDriver driver) {
        PageFactory.initElements(driver, this);
    }

    public void login(String user, String pass) {
        usernameField.sendKeys(user);
        passwordField.sendKeys(pass);
    }
}

How the Driver Actually Gets Passed In

PageFactory.initElements(driver, this) is where all the real work happens.

  1. Reflection scan — it scans the class (this) for every field annotated @FindBy.
  2. Locator built — for each field, it constructs an ElementLocator via DefaultElementLocatorFactory(driver). This is the exact point where driver gets used — to know how to eventually find the element.
  3. Proxy created — instead of calling findElement() right away, it creates a dynamic proxy (Proxy.newProxyInstance) for each WebElement field, backed by a LocatingElementHandler (implements InvocationHandler).
  4. Field assigned — the proxy is set into the field via reflection: field.set(page, proxy).
new LoginPage(driver) → constructor runs
PageFactory.initElements(driver, this) → scans @FindBy fields
Each field replaced with a dynamic Proxy (not a real WebElement yet)
.click() / .sendKeys() called on the field → proxy intercepts
Only NOW does driver.findElement(By...) actually fire
Why this matters (the interview payoff): Because lookup is lazy, PageFactory elements do not throw NoSuchElementException at page-object construction time — even if the element isn't on the DOM yet. The exception only surfaces when you actually interact with the element.

One-Liners to Remember

  • POM = pattern. PageFactory = one implementation of that pattern.
  • initElements() is where driver gets bound to locators, via a locator factory.
  • Fields become proxies, not real elements, until first use.
  • Laziness is the reason PageFactory doesn't blow up on construction for elements not yet on the DOM.
  • Most modern frameworks favor plain constructors over PageFactory, citing debuggability.
