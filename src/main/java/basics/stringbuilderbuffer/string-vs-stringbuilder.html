Why StringBuilder / StringBuffer over String?

The question interviewers ask to check whether you actually understand Java memory, not just the syntax. Here's the full answer, with the diagrams and benchmarks to back it up.

One-line answer: String is immutable — every concatenation creates a brand-new object in memory. In a loop, that means throwaway garbage on every iteration. StringBuilder (and StringBuffer) use a mutable, resizable buffer, so repeated modification happens in place — no repeated allocation, no GC churn.
01

The root cause: String is immutable

Once a String object is created, its internal character array can never change. Any "modification" — concatenation, replace, substring — returns a new object. The old one just sits in memory until garbage collected.

String concatenation in a loop 3 objects created
"Test"+= "1"
"Test1"+= "2"
"Test12"← final reference

Every += abandons the previous object. The strikethrough ones are now unreachable garbage — pure allocation cost for no benefit.

StringBuilder.append() in a loop 1 object, resized in place
[T e s t _ _]
[T e s t 1 _]
[T e s t 1 2]

Same char array, mutated directly. It only reallocates if it outgrows its internal capacity — and even then, it grows geometrically, not per-append.

02

Why it matters: the cost compounds

Concatenating n times with String is roughly O(n²) — each new string re-copies everything before it. StringBuilder amortizes to O(n). This is invisible at 5 iterations and very visible at 50,000 (e.g. building a large report, a huge XPath, or log text row-by-row in an automation run).

~4800ms

~18ms

Illustrative proportions for ~50,000 concatenations of a short string — exact numbers vary by JVM/heap settings, but the order-of-magnitude gap is consistent and easy to reproduce yourself (code below).

Benchmark.java
public class Benchmark {
    public static void main(String[] args) {
        int iterations = 50_000;

        // ---- String: creates a new object every single loop ----
        long start = System.nanoTime();
        String result = "";
        for (int i = 0; i < iterations; i++) {
            result += i;   // new String object each time
        }
        printElapsed("String", start);

        // ---- StringBuilder: mutates one internal buffer ----
        start = System.nanoTime();
        StringBuilder sb = new StringBuilder();
        for (int i = 0; i < iterations; i++) {
            sb.append(i);   // in-place, no new object per iteration
        }
        printElapsed("StringBuilder", start);
    }
}

04

Which one, when

String

  • Value is fixed or changes rarely
  • Used as a HashMap/HashSet key (needs stable hashcode)
  • Small number of concatenations (JVM compiler often optimizes simple cases anyway)
→ Default choice for plain data

StringBuilder

  • Building text inside a loop, single-threaded
  • Local variable inside one method — never shared across threads
  • Most real-world "building a string" scenarios, including test automation code
→ Default choice for building/mutating text

StringBuffer

  • The same buffer is genuinely accessed by multiple threads
  • You need built-in synchronization without adding your own locks
  • Legacy codebases already using it
→ Rare in new code — StringBuilder + your own sync usually wins
05

Where this shows up in Selenium / test automation

This isn't just theory for the interview — it's a real pattern in framework code you've probably already written.

Common case

Building a dynamic XPath/CSS locator, an assertion failure message, or a test execution log line by appending values across several conditions/loops — e.g. iterating over a table's rows and columns to build one combined validation report string.

DynamicLocatorBuilder.java
// Building an XPath by concatenating conditions in a loop
StringBuilder xpath = new StringBuilder("//table//tr");
for (String col : expectedColumns) {
    xpath.append("[td[contains(text(),'")
         .append(col)
         .append("')]]");
}
driver.findElement(By.xpath(xpath.toString()));

// Same idea for a soft-assertion summary across many rows
StringBuilder report = new StringBuilder();
for (RowResult row : results) {
    if (!row.isPassed()) {
        report.append("Row ").append(row.getIndex())
              .append(" mismatch: ").append(row.getDiff())
              .append("\n");
    }
}
Assert.assertTrue(report.length() == 0, report.toString());

With String += here, every row would allocate a new full-length string — wasteful, and it gets worse the more rows/columns your test data has. StringBuilder is the natural fit since this buffer never leaves the current thread.

30-second interview answer

If asked to say it out loud in the room, structure it like this:

  • 1.Immutability first: "String is immutable in Java — every concatenation creates a new object instead of modifying the existing one."
  • 2.Cost: "In a loop, that means repeated allocation and garbage collection overhead — it degrades toward O(n²) for n concatenations."
  • 3.The fix: "StringBuilder/StringBuffer hold a mutable, resizable character buffer, so repeated appends happen in place — O(n) overall."
  • 4.The difference between the two: "StringBuffer's methods are synchronized — thread-safe but slower. StringBuilder isn't synchronized, so it's faster and is the default choice unless the buffer is truly shared across threads."
  • 5.Anchor it to real code: "For example, I use StringBuilder when building dynamic XPath locators or assembling multi-row validation messages in my test framework."
