Maven / Enterprise Networking

When Maven Central
is off-limits

Two ways around a locked-down company network: point Maven at an internal artifact server (Nexus / JFrog Artifactory), or hand-install the jar straight into your local repo. Here's exactly what changes, and where.

Request path — blocked vs. redirected
Reading the diagram Your machine never talks to Maven Central directly. It only knows about the internal repo — the internal repo is the one with permission to reach the outside world and cache what it fetches.
01

Route 1 — redirect Maven via settings.xml

This file lives at ~/.m2/settings.xml (or $MAVEN_HOME/conf/settings.xml for a machine-wide default). It's not your project's pom.xml — it's user/machine-level config, which is exactly why it's the right place for "how do I even reach a repo" rules that shouldn't be committed to source control.

~/.m2/settings.xml 
<settings>

  <!-- ① tells Maven "for ANY request, go here instead" -->
  <mirrors>
    <mirror>
      <id>company-nexus</id>
      <name>Internal Nexus mirror of central</name>
      <url>https://nexus.mycompany.com/repository/maven-public/</url>
      <mirrorOf>*</mirrorOf>
    </mirror>
  </mirrors>

  <!-- ② credentials for that same repo — id MUST match the mirror's id -->
  <servers>
    <server>
      <id>company-nexus</id>
      <username>sumit.sagar</username>
      <password>{{encrypted-or-token}}</password>
    </server>
  </servers>

  <!-- ③ optional: only needed if repo isn't set as a full mirror,
       e.g. you want ONE extra repo alongside central -->
  <profiles>
    <profile>
      <id>internal-repo</id>
      <repositories>
        <repository>
          <id>company-nexus</id>
          <url>https://nexus.mycompany.com/repository/maven-public/</url>
        </repository>
      </repositories>
    </profile>
  </profiles>
  <activeProfiles>
    <activeProfile>internal-repo</activeProfile>
  </activeProfiles>

</settings>
① <mirrors>The heavy lever. mirrorOf = * means "every single dependency request, no matter what repo the pom.xml declares, gets rewritten to this URL." This is what actually stops traffic from ever leaving toward Maven Central.
② <servers>Just credentials — Nexus/JFrog usually sit behind auth. The id here is a foreign key back to the mirror/repository block with the same id; that's how Maven knows which URL these creds belong to.
③ <profiles>Use this instead of a full mirror when you only want to add an internal repo (for private/internal artifacts) without redirecting everything. Most corporate setups use ①+② because Nexus/JFrog already proxy central internally.
Common gotcha If id in <server> doesn't exactly match the id in <mirror>/<repository>, Maven fetches the URL fine but silently fails auth — you'll see 401 Unauthorized or 403 in the log, not a "wrong config" message.

02

Route 2 — manually install the jar into .m2

No network route to any repo (or the dependency isn't published anywhere internal, e.g. a vendor gave you a jar directly)? Skip resolution entirely and place the artifact into your local repository yourself, in the exact folder layout Maven expects.

Where Maven actually looks Your local repo (~/.m2/repository) is not a flat folder — it mirrors groupId.artifactId.version as nested directories. Manual copy-paste in the wrong shape is the #1 reason "I installed it but Maven still says missing artifact."
 ~/.m2/repository/
 └── com/
    └── mycompany/ ← groupId, dots become slashes
        └── pricing-utils/ ← artifactId
            └── 2.3.1/ ← version
                ├── pricing-utils-2.3.1.jar ← the artifact itself
                └── pricing-utils-2.3.1.pom ← generated metadata, do NOT skip

You get that layout for free — for a single command, run:

terminal
mvn install:install-file \
  -Dfile=/path/to/pricing-utils-2.3.1.jar \
  -DgroupId=com.mycompany \
  -DartifactId=pricing-utils \
  -Dversion=2.3.1 \
  -Dpackaging=jar \
  -DgeneratePom=true

-Dfile

Path to the jar you already have on disk — from a vendor, a colleague, or downloaded on a machine that does have access.

-DgroupId / -DartifactId / -Dversion

These three together decide the folder path shown above. They must exactly match what your pom.xml's <dependency> block declares, or Maven will look in the wrong nested folder and still report it missing.

-DgeneratePom=true

Auto-creates the minimal .pom file Maven needs alongside the jar. Without it, some Maven versions refuse to resolve the artifact even though the jar is physically present.

Reference it in pom.xml — same as any normal dependency

Once installed, it's indistinguishable from a jar Maven downloaded itself. No special syntax needed in the consuming project.

pom.xml
<dependency>
  <groupId>com.mycompany</groupId>
  <artifactId>pricing-utils</artifactId>
  <version>2.3.1</version>
</dependency>
Doing it by hand, no plugin If mvn itself can't run install:install-file for some reason (e.g. resolving the plugin also needs a network you don't have), you can literally create the three files/folders in the tree above yourself and drop the jar in — Maven doesn't care how they got there, only that the layout is correct.

Which route, when

SituationUse
Company has Nexus/JFrog, proxies Maven Central internallyRoute 1 — <mirrors>, set once, works for every dependency forever
Internal-only library your team publishes (not on any public repo)Route 1, but as an added <repository> in a profile, not a full mirror
One-off vendor jar, no internal repo entry exists for itRoute 2 — install:install-file, quick and local to your machine
Need the whole team/CI to have it, not just your laptopUpload it into Nexus/JFrog once (via their UI or mvn deploy:deploy-file), then it's Route 1 for everyone else
settings.xml lives per-user (~/.m2) or per-machine (Maven install dir) — never in the repo. Local .m2 installs are per-machine only; for a team/CI, push the artifact into Nexus/JFrog instead so everyone resolves it the normal way.
