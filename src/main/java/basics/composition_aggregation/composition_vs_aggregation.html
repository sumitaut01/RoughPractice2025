1. The Core Concept

Both Composition and Aggregation are forms of the "HAS-A" relationship between classes — as opposed to Inheritance, which is an "IS-A" relationship. The difference between them comes down to one question:

Who owns the lifecycle of the contained object?
If the container creates and destroys the part, and the part cannot meaningfully exist without it → Composition
If the container just holds a reference to something that exists independently and can outlive it, or be shared elsewhere → Aggregation
Composition (strong ownership, filled diamond in UML) ┌────────────┐ ┌────────────┐ │ Car │◆──────▶│ Engine │ Engine is created inside Car, └────────────┘ └────────────┘ dies when Car is destroyed. Aggregation (weak ownership, hollow diamond in UML) ┌────────────┐ ┌────────────┐ │ Team │◇──────▶│ Player │ Player exists independently, └────────────┘ └────────────┘ can belong to another Team too.

2. Quick Comparison Table

Aspect Composition Aggregation
Relationship strength Strong ("owns-a") Weak ("has-a")
Lifecycle Part dies when whole dies Part can outlive the whole
Object creation Usually created inside the container (e.g. in constructor, new) Usually passed in from outside (constructor injection / setter)
Sharing Not shared with other objects Can be shared across multiple containers
UML notation Filled diamond ◆ Hollow diamond ◇
Test framework example A LoginPage creates its own WebDriverWait internally A TestSuiteRunner holds a list of TestCase objects supplied to it

3. Composition — Deep Dive

In composition, the "whole" object is responsible for creating and managing the "part." If you delete the whole, the part goes with it — there's no independent existence.

Example: Car and Engine

class Engine {
    private final String type;

    public Engine(String type) {
        this.type = type;
    }

    public void start() {
        System.out.println(type + " engine starting...");
    }
}

class Car {
    // Engine is created INSIDE Car — Car owns its lifecycle entirely.
    private final Engine engine;

    public Car(String engineType) {
        this.engine = new Engine(engineType); // created here, not passed in
    }

    public void drive() {
        engine.start();
        System.out.println("Car is driving");
    }
}

public class Main {
    public static void main(String[] args) {
        Car car = new Car("V8");
        car.drive();
        // There is no way to grab the Engine from outside and reuse it
        // elsewhere. When `car` goes out of scope, its Engine goes too.
    }
}
Key signal: the new Engine(...) call happens inside the Car class. No one hands the engine to the car from outside.

4. Aggregation — Deep Dive

In aggregation, the "part" is created independently — usually outside the container — and simply handed a reference. The part can be reused elsewhere, and it survives even if the container is discarded.

Example: Team and Player

class Player {
    private final String name;

    public Player(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}

class Team {
    // Players are created OUTSIDE and passed in — Team does not own their lifecycle.
    private final List<Player> players;

    public Team(List<Player> players) {
        this.players = players; // just holds a reference
    }

    public void listPlayers() {
        players.forEach(p -> System.out.println(p.getName()));
    }
}

public class Main {
    public static void main(String[] args) {
        Player messi = new Player("Messi");
        Player ronaldo = new Player("Ronaldo");

        Team barcelona = new Team(List.of(messi));
        // `messi` still exists independently and could be added to
        // a different Team object, or a national squad, etc.

        barcelona.listPlayers();
    }
}
Key signal: players is passed into the constructor — Team never calls new Player(...) itself.

5. Applying This to a Test Automation Framework

This distinction shows up constantly in Selenium/TestNG-style frameworks — knowing which one you're using drives good, low-coupling design decisions.

Composition Page Object owning its own wait helper

class LoginPage {
    private final WebDriver driver;
    // Wait is created internally — tightly bound
    // to this page's lifecycle, never shared.
    private final WebDriverWait wait;

    public LoginPage(WebDriver driver) {
        this.driver = driver;
        this.wait = new WebDriverWait(
            driver, Duration.ofSeconds(10));
    }

    public void login(String user, String pass) {
        wait.until(ExpectedConditions
            .visibilityOfElementLocated(
                By.id("username")))
            .sendKeys(user);
        driver.findElement(By.id("password"))
              .sendKeys(pass);
        driver.findElement(By.id("loginBtn"))
              .click();
    }
}

Aggregation Test Suite holding shared, reusable Test Cases

class TestCase {
    private final String name;
    public TestCase(String name) { this.name = name; }
    public void run() {
        System.out.println("Running: " + name);
    }
}

class TestSuiteRunner {
    // TestCases are built elsewhere (e.g. by TestNG,
    // a factory, or a config reader) and just handed in.
    private final List<TestCase> testCases;

    public TestSuiteRunner(List<TestCase> testCases) {
        this.testCases = testCases;
    }

    public void runAll() {
        testCases.forEach(TestCase::run);
    }
}

// Same TestCase objects could be reused in a different
// suite (e.g. a "smoke" suite AND a "regression" suite)
// without being duplicated or destroyed.

A realistic hybrid framework example: WebDriverManager

Here's a pattern common in hybrid Selenium + API + DB frameworks — a TestContext that composes its own driver manager (owns it, creates it, kills it), but aggregates a shared ConfigReader that's built once and reused across every test in the run. 

class TestContext {
    // COMPOSITION: driver manager is created and destroyed with this context
    private final DriverManager driverManager;

    // AGGREGATION: config is built once at suite startup and shared
    // across every TestContext instance — this class doesn't own it.
    private final ConfigReader config;

    public TestContext(ConfigReader sharedConfig) {
        this.config = sharedConfig;                 // injected, shared
        this.driverManager = new DriverManager(sharedConfig); // owned, private
    }

    public void tearDown() {
        driverManager.quit(); // only TestContext controls this
        // config is left untouched — other TestContexts still need it
    }
}

6. Common Pitfalls

Pitfall 1 — Fake composition: Creating a "new" object every time but still passing dependencies in from outside (e.g. driver, config) doesn't make something composition. Composition is about who owns the part's lifecycle, not whether new appears somewhere.
Pitfall 2 — Sharing a "composed" object by accident: If two Page Objects end up holding the same WebDriverWait instance because someone passed a reference around, you no longer have composition — you've drifted into (probably unintended) aggregation, and now a change in one page can affect another.
Pitfall 3 — Over-composing framework utilities: Things like ExtentReportManager, ConfigReader, or a shared DBConnectionPool should almost always be aggregated (built once, injected everywhere) — not re-created inside every class that needs them. Re-creating them as composition leads to duplicate connections/reports and inconsistent state.

7. Which One Should I Use? — Quick Checklist

Ask yourself...If YES →
Should the part be destroyed when the container is? Composition
Does the part make sense only in the context of this one container? Composition
Will multiple objects need to share this same instance? Aggregation
Is this object built once at suite/framework startup (config, driver factory, DB pool, report manager)? Aggregation
Would unit testing this class require mocking the part and injecting it? Aggregation (favor constructor injection)
Rule of thumb for frameworks: Page Objects and step-specific helpers lean toward Composition. Cross-cutting framework infrastructure (config, driver factories, reporting, DB connections, test data providers) leans toward Aggregation via dependency injection.
