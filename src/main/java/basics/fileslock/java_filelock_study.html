FileLock in Java NIO

Purpose, working code, and how it differs from thread-level synchronization (incl. ThreadLocal).

1What is FileLock

java.nio.channels.FileLock represents a lock on a region (or the whole) of a file, obtained through a FileChannel (or AsynchronousFileChannel). It's part of NIO's file API, introduced to let a program coordinate access to a file across processes — even processes outside the JVM, written in a different language entirely.

Key mental model: a FileLock is like a reservation ticket on a file that the operating system enforces (or at least tracks), not something the JVM enforces internally the way synchronized does.

2Why it exists (purpose)

  • Inter-process coordination: stop two separate programs (or two instances of the same program) from writing to the same file simultaneously — e.g. a log file, a config file, a lock/pid file, or a shared report/Excel export that multiple test runners might touch.
  • Data integrity: avoid interleaved/corrupted writes when multiple writers exist.
  • Single-instance enforcement: a very common pattern — acquire a lock on a .lock file at startup; if it fails, another instance is already running.
  • Region-level control: you can lock just a byte range of a large file instead of the whole thing, letting different parts be updated independently.
Important nuance: on most platforms FileLock is advisory, not mandatory — it only stops other cooperating programs that also try to acquire a lock. A process that ignores locking entirely can still read/write the file. (On Windows it tends to be enforced more strictly at the OS level; on Unix it's purely advisory.)

3Exclusive vs Shared locks

TypeMeaningTypical use
ExclusiveOnly one holder at a time; blocks other exclusive and shared locks on the overlapping region.Writing to the file
SharedMultiple holders allowed simultaneously, but blocks any exclusive lock.Reading the file (readers don't block each other)

Not every OS/filesystem supports shared locks — check FileLock.isShared() after acquiring; the JVM may silently upgrade to exclusive if shared isn't supported.

4Sample code

Basic exclusive lock (write coordination)

import java.io.RandomAccessFile;
import java.nio.channels.FileChannel;
import java.nio.channels.FileLock;
import java.nio.charset.StandardCharsets;

public class FileLockDemo {
    public static void main(String[] args) throws Exception {
        try (RandomAccessFile raf = new RandomAccessFile("report.txt", "rw");
             FileChannel channel = raf.getChannel()) {

            // Blocks until the lock is available (exclusive lock on whole file)
            try (FileLock lock = channel.lock()) {
                System.out.println("Lock acquired: " + lock.isShared());

                // safe to write now — no other cooperating process can write concurrently
                byte[] data = "Test run result: PASS\n".getBytes(StandardCharsets.UTF_8);
                channel.write(java.nio.ByteBuffer.wrap(data), channel.size());
            } // lock auto-released here (try-with-resources)
        }
    }
}

Locking just a byte-range (region lock)

// Lock only bytes 0..99 of the file, exclusive
FileLock lock = channel.lock(0, 100, false); // false = exclusive, true = shared

Single-instance app guard (very common real-world use)

RandomAccessFile raf = new RandomAccessFile("app.lock", "rw");
FileChannel channel = raf.getChannel();
FileLock lock = channel.tryLock();

if (lock == null) {
    System.out.println("Another instance is already running. Exiting.");
    System.exit(1);
}
// else: this is the only instance — keep lock held for app lifetime

5lock() vs tryLock()

MethodBehavior
channel.lock()Blocks the calling thread until the lock becomes available (or throws). Good when you're willing to wait.
channel.tryLock()Non-blocking — returns immediately. Returns the FileLock if acquired, or null if it's currently held elsewhere. Good for "check and bail out" scenarios like the single-instance guard above.

6How this differs from thread-level locking (and ThreadLocal)

This is the part worth being precise about — FileLock, thread synchronization (synchronized / ReentrantLock), and ThreadLocal solve three different problems, even though all three sound like "concurrency control."

FileLock

  • Scope: across processes (even across the OS)
  • Enforced by: the operating system (advisory on Unix)
  • Protects: a file or byte-range of a file
  • Not reentrant — a second lock() on the same region from the same JVM throws OverlappingFileLockException

synchronized / ReentrantLock

  • Scope: threads within the same JVM
  • Enforced by: the JVM's monitor/lock mechanism
  • Protects: shared in-memory objects/critical sections
  • ReentrantLock (and intrinsic locks) are reentrant — same thread can re-acquire

And ThreadLocal — a different category entirely

ThreadLocal<T> is not a locking mechanism at all. It doesn't coordinate access to shared data — it avoids sharing by giving each thread its own independent copy of a variable. There's nothing to "lock" because nothing is shared.

private static final ThreadLocal<SimpleDateFormat> FORMATTER =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

// Each thread calling FORMATTER.get() gets its own SimpleDateFormat instance —
// no synchronization needed because there's no shared object to contend over.
Common mix-up: people sometimes assume ThreadLocal is "for locking things per thread." It isn't — it's the opposite strategy. Locking (FileLock, synchronized) says "only one at a time may touch this shared thing." ThreadLocal says "give everyone their own thing, so there's nothing to contend over." In QA automation this shows up a lot with per-thread WebDriver instances in parallel Selenium/TestNG runs — ThreadLocal<WebDriver> instead of locking a single shared driver.

7Gotchas to remember

  • FileLock is per JVM, not per thread — two threads in the same JVM can't hold separate locks on the same file region; the second attempt throws OverlappingFileLockException. Use a normal Java lock (e.g. ReentrantLock) to coordinate threads within the same JVM first, then FileLock for cross-process safety.
  • Always release locks (use try-with-resources on FileLock) — an unreleased lock can block other processes indefinitely.
  • Advisory locking means a misbehaving process can bypass it entirely — don't rely on it as a security boundary, only as cooperative coordination.
  • Behavior can vary by OS/filesystem (especially over NFS) — test on your actual deployment target.
