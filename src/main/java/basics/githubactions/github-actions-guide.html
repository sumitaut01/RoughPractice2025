Running Selenium & RestAssured Suites on GitHub Actions

You already know the basics — YAML config, OS/browser selection, selective test runs, and auto-attached reports. This is the fuller picture: how the pieces fit together, and the scenarios that come up once a suite goes from "runs on my machine" to "runs on every PR."

01

§1 The four building blocks

Everything below is a combination of these. Once these click, reading any workflow file — yours or someone else's — gets a lot faster.

TermWhat it isIn your context
WorkflowOne YAML file, one automated process, triggered by an event.github/workflows/regression.yml
JobA set of steps that run together on one runner (VM)"run-selenium-tests", "run-api-tests"
StepA single command or a reusable Action inside a jobmvn test, or actions/checkout@v4
RunnerThe actual VM the job executes onubuntu-latest, windows-latest
Jobs run in parallel by default. If run-selenium-tests and run-api-tests are separate jobs, they'll fire simultaneously on separate runners unless one declares needs: run-selenium-tests. That's the mechanism behind splitting UI and API suites into independent, faster lanes.

§2 Anatomy of a test workflow

A minimal but realistic setup for a Java/Maven project with TestNG, Selenium and RestAssured together.

.github/workflows/regression.ymlYAML
name: Regression Suite

# --- 1. When it runs ---
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

# --- 2. What it runs on and with ---
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 30

    steps:
      - uses: actions/checkout@v4

      - name: Set up JDK 17
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
          cache: maven

      - name: Run TestNG suite
        run: mvn -B clean test -DsuiteXmlFile=testng.xml

Two things worth noticing that aren't obvious from the docs:

  • cache: maven on setup-java alone caches ~/.m2 keyed off your pom.xml hash — no separate actions/cache step needed for a standard Maven build.
  • timeout-minutes matters more for UI suites than API suites — a hung WebDriver session will otherwise burn your full runner minutes budget before Actions' own 6-hour default cutoff kicks in.

§3 OS and browser matrix

strategy.matrix multiplies your job — one combination per runner, all in parallel. For Selenium 4+, you don't need Selenium Manager binaries or a separate driver-download action; Selenium Manager resolves the right driver automatically per OS/browser at runtime.

.github/workflows/cross-browser.ymlYAML
jobs:
  cross-browser:
    strategy:
      fail-fast: false       # one failing combo shouldn't cancel the rest
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        browser: [chrome, firefox, edge]
        exclude:
          - os: macos-latest
            browser: edge       # edge isn't preinstalled on macos runners

    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '17', distribution: 'temurin', cache: maven }

      - name: Run suite for ${{ matrix.browser }}
        run: mvn -B test -Dbrowser=${{ matrix.browser }}
        env:
          HEADLESS: true
Headless is not optional on Actions runners. There's no display server by default. Either run Chrome/Firefox in --headless=new mode from your driver options class, or add xvfb for cases where a library genuinely needs a real display (rare with modern Selenium).

That single matrix block above produces 8 parallel jobs (3 OS × 3 browsers, minus 1 excluded) — visible as separate rows in the Actions run summary, each with its own logs and pass/fail state.

§4 Running a few tests vs. the full suite

This is entirely a Maven/TestNG concern — Actions just passes through whatever flags or suite file you give it. Three levels of control:

1 · By TestNG group

workflow stepYAML
- name: Run smoke group only
  run: mvn -B test -Dgroups=smoke

2 · By suite XML

workflow stepYAML
- name: Run regression suite file
  run: mvn -B test -DsuiteXmlFile=suites/regression.xml

3 · Operator's choice, at trigger time

Combine this with a workflow_dispatch input so a teammate can pick the scope from the Actions "Run workflow" button instead of editing YAML:

.github/workflows/on-demand.ymlYAML
on:
  workflow_dispatch:
    inputs:
      suite:
        description: 'Which suite to run'
        required: true
        default: 'smoke'
        type: choice
        options: [smoke, regression, full]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run selected suite
        run: mvn -B test -DsuiteXmlFile=suites/${{ github.event.inputs.suite }}.xml

This is the closest thing to a manual "run button with options" that Actions offers — no custom UI needed.

§5 Spinning up a database for RestAssured/DB tests

Since your hybrid framework validates responses against Postgres/Oracle directly, this is the piece that's easy to miss: Actions can run a service container alongside your job, so tests hit a real, disposable database instead of mocks.

.github/workflows/api-db-tests.ymlYAML
jobs:
  api-tests:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: test_user
          POSTGRES_PASSWORD: test_pass
          POSTGRES_DB: x4v_test
        ports: ['5432:5432']
        options: >-
          --health-cmd=pg_isready
          --health-interval=10s
          --health-timeout=5s
          --health-retries=5

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '17', distribution: 'temurin', cache: maven }

      - name: Run API + DB assertions
        run: mvn -B test -Dgroups=api
        env:
          DB_URL: jdbc:postgresql://localhost:5432/x4v_test
          DB_USER: test_user
          DB_PASS: test_pass

The health-cmd block matters — without it, your first test can fire before Postgres finishes initializing, giving a flaky "connection refused" on run one that mysteriously passes on retry.

Oracle doesn't have an official lightweight service-container image the way Postgres does. The common pattern is to point the workflow at a persistent test Oracle instance (via secrets for host/credentials) rather than spinning one up per run.

§6 Attaching reports automatically

"Attaches itself" covers two different things in Actions — worth separating, since they solve different problems.

A · Artifacts (download-and-view)

Any file the job produces — Surefire HTML, an Extent/Allure report, screenshots on failure — gets zipped and attached to the run summary with actions/upload-artifact.

workflow stepYAML
- name: Run tests
  run: mvn -B test

- name: Upload TestNG report
  if: always()            # upload even when tests fail
  uses: actions/upload-artifact@v4
  with:
    name: testng-report
    path: test-output/
    retention-days: 14

if: always() is the detail that trips people up most — by default, a step is skipped once any prior step fails, so a red run silently uploads nothing unless you say otherwise.

B · Inline run summary (no download needed)

For a pass/fail count visible directly on the Actions run page — not just a zip to open — either write to $GITHUB_STEP_SUMMARY, or use a community action like dorny/test-reporter that parses your Surefire/TestNG XML into a rendered summary with per-test results.

workflow stepYAML
- name: Publish test summary
  if: always()
  uses: dorny/test-reporter@v1
  with:
    name: TestNG Results
    path: 'target/surefire-reports/*.xml'
    reporter: java-junit

C · A hosted HTML report (Allure-style)

If you're generating an Allure report, pair the upload step with actions/deploy-pages (or publish to a gh-pages branch) so the report is a live link in the PR, not just a downloadable zip — useful when non-technical reviewers need to see it without pulling artifacts.

§7 Secrets — what they are, and where to set them

A secret is an encrypted key/value pair stored by GitHub, outside your repo's code, that a workflow can read at run time but nobody can read back through the UI or the logs once it's saved. This is where DB passwords, API base URLs for staging vs. prod, and any credential your suite needs live — never inline in the YAML, never committed to the repo.

Why not just hardcode it

  • The YAML file is public history the moment it's pushed — anyone with read access to the repo (or a fork, if public) can see it, forever, even if you remove it later in a new commit.
  • GitHub automatically masks a secret's value in the run logs — any place it would print, you see *** instead. Hardcoded values get no such protection.
  • The same workflow file can run against different environments (staging, prod) just by swapping which secret is wired to which environment — no code change needed.

Where to create one

Repository secret

Repo → Settings → Secrets and variables → Actions

Click New repository secret, give it a name (e.g. DB_PASSWORD) and a value. Scoped to this one repo — the most common choice for a single test-automation project.

Environment secret

Repo → Settings → Environments → (staging/prod) → Secrets

Create an environment first (e.g. "staging"), then add secrets under it. Lets the same secret name (API_BASE_URL) hold a different value per environment, and can require manual approval before a job using it runs.

Organization secret

Org → Settings → Secrets and variables → Actions

Shared across many repos in the org — useful for something like a shared test-account password used by several automation projects. Access can be restricted to selected repos.

Non-secret config

Same screen → the "Variables" tab

For values that aren't sensitive (a base URL that's fine to be public) use a repository variable instead — referenced as ${{ vars.NAME }}. Keeps the secrets list to things that actually need masking.

Using it in the workflow

.github/workflows/api-db-tests.ymlYAML
jobs:
  api-tests:
    runs-on: ubuntu-latest
    # optional: pin this job to an environment to pull that env's secrets
    environment: staging

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '17', distribution: 'temurin', cache: maven }

      - name: Run RestAssured suite
        run: mvn -B test -Dgroups=api
        env:
          DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
          API_BASE_URL: ${{ secrets.STAGING_API_URL }}

The env: block maps each secret onto a plain environment variable your Java process can read the normal way — System.getenv("DB_PASSWORD") — so nothing in your test code or pom.xml needs to know it came from GitHub at all.

A secret is only ever readable inside the run that references it. You can't view its value again in the Settings UI after saving — only overwrite it. If you lose track of what a credential was, rotate it and update the secret rather than trying to retrieve the old one.
Pull requests from forks don't get secrets by default. This is deliberate — it stops an outside contributor's PR from exfiltrating your credentials via a modified workflow file. If external contributors need CI to run, that typically means a maintainer-approved run or a separate, secret-free lane for fork PRs.

§8 Trigger scenarios worth knowing

The on: block is where most of the practical flexibility lives.

on: pull_request

Gate before merge

Runs the smoke/regression suite on every PR against main. Pair with branch protection rules to make it a required check.

on: schedule (cron)

Nightly full regression

cron: '0 2 * * *' — run the entire suite (all browsers, all groups) overnight when runner time doesn't compete with dev workflow.

on: workflow_dispatch

Manual, parameterized run

A teammate clicks "Run workflow" and picks suite/browser/environment from dropdowns — no YAML edits needed for a one-off run.

on: workflow_run

Chained after deploy

Trigger the test workflow automatically once a separate "Deploy to staging" workflow completes successfully — useful for post-deploy smoke checks.

Nightly full-suite example

.github/workflows/nightly.ymlYAML
on:
  schedule:
    - cron: '0 2 * * *'    # 02:00 UTC daily
  workflow_dispatch:          # plus a manual override button

jobs:
  full-regression:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '17', distribution: 'temurin', cache: maven }
      - run: mvn -B test -DsuiteXmlFile=suites/full.xml
Combine workflow_dispatch with the environment: field from §7 to let a teammate pick staging vs. prod secrets at run time — the same mechanism as the suite-selection dropdown in §4, applied to environment instead of scope.

§9 Putting it together

One workflow, two independent jobs — UI suite across a browser matrix, API suite against a live Postgres service — both reporting back to the same run.

.github/workflows/full-regression.ymlYAML
name: Full Regression

on:
  pull_request:
    branches: [main]
  workflow_dispatch: {}

jobs:
  ui-tests:
    strategy:
      fail-fast: false
      matrix:
        browser: [chrome, firefox]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '17', distribution: 'temurin', cache: maven }
      - name: Run Selenium suite
        run: mvn -B test -Dgroups=ui -Dbrowser=${{ matrix.browser }}
      - name: Upload UI report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: ui-report-${{ matrix.browser }}
          path: test-output/

  api-tests:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env: { POSTGRES_USER: test_user, POSTGRES_PASSWORD: test_pass, POSTGRES_DB: x4v_test }
        ports: ['5432:5432']
        options: --health-cmd=pg_isready --health-interval=10s --health-retries=5
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '17', distribution: 'temurin', cache: maven }
      - name: Run RestAssured suite
        run: mvn -B test -Dgroups=api
        env:
          DB_URL: jdbc:postgresql://localhost:5432/x4v_test
          API_BASE_URL: ${{ secrets.STAGING_API_URL }}
      - name: Upload API report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: api-report
          path: target/surefire-reports/

ui-tests and api-tests run as two independent jobs — no needs: between them — so they execute at the same time and the whole run finishes in roughly the length of the slower one, not the sum of both.

§10 Before you ship the workflow

  • Maven/Gradle dependency caching is enabled (cache: maven on setup-java, or an explicit actions/cache step)
  • Report/artifact upload steps use if: always() so failures still leave evidence behind
  • Browser runs are explicitly headless — no assumption of a display server on the runner
  • Secrets (DB creds, API base URLs) come from secrets.*, never hardcoded in the YAML — set at the right scope (repo / environment / org)
  • fail-fast: false is set on any matrix where you want every combination's result, not just the first failure
  • A timeout-minutes is set per job so a hung WebDriver session can't quietly eat the whole runner budget
  • Service container health checks (--health-cmd) are in place before DB-dependent steps run
Written for a Java · Selenium · TestNG · RestAssured stack — adjust runner images, cache keys, and service containers if yours differs.
