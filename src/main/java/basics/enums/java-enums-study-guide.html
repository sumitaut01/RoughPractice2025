java · type system

enum.

A fixed, named set of singleton instances, closed at compile time. Not a string. Not an int. A type the compiler can actually check.

01 — the problem enums solve

Before enums, people faked it

Every language eventually needs "one of a fixed set of things." Java's answer, before enum existed (pre‑Java 5), was the int constant or String constant pattern. It compiled fine. It also broke in ways the compiler couldn't see.

the old way fragile

public static final int STATUS_PENDING = 0;
public static final int STATUS_SHIPPED = 1;
public static final int STATUS_DELIVERED = 2;

void ship(int status) {
  if (status == STATUS_SHIPPED) { /* ... */ }
}

ship(STATUS_DELIVERED);  // compiles
ship(99);                    // also compiles!
ship(DAYS_IN_WEEK);        // also compiles! wrong constant, same type
  • Any int is accepted — there's no way to say "only these four ints."
  • Debugger shows 0, not SHIPPED — meaningless in a breakpoint.
  • No namespace — constants from unrelated groups mix freely.

the enum way checked

public enum OrderStatus { PENDING, SHIPPED, DELIVERED }

void ship(OrderStatus status) {
  if (status == OrderStatus.SHIPPED) { /* ... */ }
}

ship(OrderStatus.DELIVERED); // fine
ship(99);                       // won't even compile
ship(Weekday.MONDAY);           // won't even compile — wrong type
  • The type itself is the constraint — impossible values don't exist.
  • IDE autocompletes the exact set. Nothing to memorize or mistype.
  • switch can warn you if a case is unhandled.
02 — what it actually is

An enum is a class. The constants are objects.

This is the part that surprises people coming from C‑style enums. In Java, OrderStatus.SHIPPED isn't a number in disguise — it's a real, singleton instance of the class OrderStatus. That's why enums can carry fields, constructors, and methods, and why == is always safe to use on them.

OrderStatus.java
public enum OrderStatus {

  PENDING("Awaiting confirmation"),
  SHIPPED("On the way"),
  DELIVERED("Completed"),
  CANCELLED("Order stopped");

  private final String description;   // every constant carries its own state

  OrderStatus(String description) {      // constructor runs once per constant, at class load
    this.description = description;
  }

  public String describe() {
    return description;
  }
}

Four constants are declared → the JVM creates exactly four objects, once, at class‑loading time. No one can create a fifth. That guarantee is what everything else below relies on.

03 — see the singleton guarantee

Exactly one instance can be "current"

Click a constant. Watch the readout — this is exactly what status == OrderStatus.SHIPPED is doing under the hood: comparing object identity, not decoding a number or parsing text.

04 — your actual question

Matching a config string to an enum — is that right?

Yes, that pattern is correct and extremely common: config files, DB columns, and JSON are text, but you want a type‑safe value inside your Java code. The enum is the boundary where a loose string becomes a checked type. The part people get wrong is which method does the matching. Try it below.

PENDINGSHIPPEDDELIVEREDCANCELLED

OrderStatus.valueOf(text) throws

String raw = config.get("status"); // "shipped"
OrderStatus s = OrderStatus.valueOf(raw);
// IllegalArgumentException:
// No enum constant OrderStatus.shipped
  • Case‑sensitive, exact match to the constant name only.
  • Throws unchecked IllegalArgumentException — easy to forget to catch.
  • Fine for trusted, internal strings (e.g. round‑tripping .name()).

custom fromString() recommended for config

private static final Map<String, OrderStatus> LOOKUP =
  Arrays.stream(values())
    .collect(toMap(e -> e.name().toLowerCase(), e -> e));

public static Optional<OrderStatus> fromString(String raw) {
  return Optional.ofNullable(
    LOOKUP.get(raw == null ? null : raw.trim().toLowerCase())
  );
}
  • Normalizes case/whitespace — config authors won't hit cryptic crashes.
  • Returns Optional — caller must consciously handle "not found," e.g. fall back to a default or fail config validation with a clear message.
  • Built once via a static Map — O(1) lookup, not a chain of if/else.
05 — using enums well

Patterns worth knowing beyond the basics

01

Never persist ordinal()

It's the constant's position (0,1,2…). Reorder or insert a constant and every stored value now means something else. Persist .name() instead, or an explicit code field you control.

02

Let the enum hold behavior, not a switch outside it

Constant‑specific method bodies ({ ... } per constant) put logic where the data lives, so adding a constant can't leave a switch statement elsewhere silently incomplete.

03

Use EnumMap / EnumSet over HashMap / HashSet

Backed by the constant's ordinal internally — faster, and iterates in declaration order. A direct, free upgrade whenever the key type is an enum.

04

Implement an interface for cross‑cutting behavior

Multiple enums (e.g. discount rules in a pricing engine) can each implement the same interface and be handled polymorphically, without a big if/else chain checking each enum's type.

05

Validate config eagerly, not deep in business logic

Parse config strings to enums at startup/load time, not on every request. A bad value should fail fast during config validation, not three services deep in a stack trace.

06

Enum singletons for genuine one‑instance types

A single‑constant enum is Joshua Bloch's recommended way to write a Singleton in Java — serialization‑safe and reflection‑safe, unlike the classic private‑constructor pattern.

recap

Three things to keep

what

A class with a fixed number of named, singleton instances — the set is closed at compile time.

why

Impossible values become uncompilable, not just unexpected. The type is the validation.

config strings

Matching text to an enum is correct — just prefer a normalizing fromString() over raw valueOf() for anything not fully trusted.
