for someone who keeps hearing "classpath" and nodding

Classpath is just a list of places to look.

Nothing more mysterious than that. The confusing part is what it's a list of, and what it's searching for. Once .java vs .class clicks, the rest — including why RestAssured suddenly can't find your schema file — falls into place.

Step 1 — where it all starts

Your .java file never actually runs

This is the one fact that unlocks everything else. When you hit Run, the JVM does not read your Test.java file line by line. It cannot — the JVM only understands one language: bytecode. Your .java file is source code written for humans. It has to be translated first.

That translation is a separate, boring, mechanical step called compilation, done by a tool called javac. It reads your source and produces a new file with the same name, but a .class extension, full of bytecode instructions the JVM actually executes.

You write
LoginTest.java
Human-readable source. Classes, methods, @Test annotations, imports.
javac
Compiler produces
LoginTest.class
Bytecode. Same logic, different alphabet — one the JVM was built to read.
loads
JVM executes it
The class loader reads the .class file and runs the bytecode. This is the only file the JVM ever touches at runtime.

So why write .java at all, if only .class gets used? Because bytecode is dense and machine-oriented — nobody wants to hand-write it, and it isn't portable across languages or tooling the way source is. .java is for you and your team; .class is what actually ships and runs. This is also exactly why a .jar file — say, testng-7.9.0.jar — is really just a zip full of pre-compiled .class files. The library authors compiled it once; you never see or need their .java source.

Step 2 — the part everyone glosses over

So what is the classpath, actually

Your compiled program is rarely just one file. A single TestNG class might reference org.testng.annotations.Test, io.restassured.RestAssured, and fifty other classes it never defined itself — they live in other .class files, bundled inside other .jars.

When the JVM hits a reference like that, it has to go find the matching .class file somewhere on disk. The classpath is simply the list of folders and jar files the JVM is allowed to search — in order — when it needs to resolve a class name. Nothing else. Not a setting, not magic — a list of locations, like a PATH environment variable, except for compiled classes instead of executables.

Where does that list come from? You almost never type it out by hand anymore. When you run through Maven or Gradle, the build tool reads your pom.xml / build.gradle, resolves every dependency (TestNG, Selenium, RestAssured...), and silently assembles the full classpath for you before handing it to the JVM. Your IDE does the same thing behind its green "Run" button. The old-school way — a raw java -cp path1:path2:path3 com.MainClass command, or a global CLASSPATH environment variable — still exists and is exactly what build tools generate for you under the hood.

Try the lookup below. It's the same thing the JVM does every time a class is referenced — walk the classpath entries in order until one of them contains a matching .class.

Step 3 — reading the symptoms

When something is "missing from classpath"

This is the phrase that shows up in stack traces and makes people panic. It just means: the class name was needed, the JVM walked every entry on its list, and none of them contained a matching .class file. Two error types show up depending on when that failure is discovered:

ClassNotFoundException

Thrown at runtime when code explicitly tries to load a class by name (e.g. a JDBC driver via Class.forName(...)) and it simply isn't on any classpath entry. Fix: the jar containing it was never added as a dependency, or your run configuration's classpath differs from the one that compiled it.

NoClassDefFoundError

The class existed at compile time — your code compiled fine against it — but at runtime it's gone. Classic cause: a dependency scope mismatch, a shaded/uber jar that dropped something during packaging, or running from a jar that wasn't built with all its dependencies bundled.

The "it works on my machine" version of this: tests pass inside the IDE but fail from the command line (or a CI pipeline). Almost always a classpath mismatch — your IDE quietly built a classpath that includes something Maven's test phase doesn't, often a resource file or an extra dependency scoped differently in pom.xml.
Step 4 — where this actually bit you

RestAssured, schema files, and classpath resources

This is the same mechanism wearing a different hat. matchesJsonSchemaInClasspath(...) doesn't take a normal filesystem path — it takes a location relative to the classpath, and asks the JVM's class loader to find that file the exact same way it finds a .class file: by scanning classpath entries.

response.then().assertThat()
    .body(matchesJsonSchemaInClasspath("schema/order-response-schema.json"));

For that call to succeed, order-response-schema.json has to physically end up inside one of the folders the JVM is scanning at runtime — not just anywhere in your project. Under Maven's standard layout, that means it belongs in src/test/resources, because Maven's build copies everything under resources into target/test-classes, and that compiled output folder is what's actually on the runtime classpath — same as compiled .class files sitting right next to it.

your-project/
├── src/
│ ├── main/
│ │ └── java/ // your app source
│ └── test/
│ ├── java/
│ │ └── OrderApiTest.java // compiles to a .class file
│ └── resources/
│ └── schema/
│ └── order-response-schema.json // plain data, not code
│
└── target/ // build output — this is on the classpath
├── classes/
└── test-classes/
├── OrderApiTest.class // compiled by javac
└── schema/
└── order-response-schema.json // copied here by Maven's resources plugin

Two gotchas this explains directly:

Putting the JSON under src/test/java instead of src/test/resources — Maven's compiler only processes .java files there and doesn't reliably copy stray non-Java files into the compiled output the same way, so matchesJsonSchemaInClasspath can't find it, even though it's sitting "right next to" your test file in the IDE's project view.
Referencing it by absolute or relative filesystem path instead (e.g. "/home/user/project/schema/x.json") works on your laptop and breaks in CI, because CI's filesystem layout is different. The whole point of loading it from the classpath instead is that it stops caring where the project physically lives — it only cares that the file made it into a compiled output folder the JVM already knows to search.
