HashMap vs Hashtable

Java interview study guide — from the basic answer to the follow-up questions.

Collections FrameworkThread safetyNullsPerformanceInternals

1. Your answer — was it correct?

Yes, but it was only the starting point.

Your answer — “HashMap is newer; Hashtable is legacy, derived from Dictionary, and Hashtable is thread-safe” — is directionally correct.

The interviewer was probably looking for the practical differences: synchronization, null handling, performance, inheritance, ordering, iteration and what you would use today.

2. The 30-second interview answer

Good answer:
“Hashtable is a legacy class from Java 1.0 and extends Dictionary. Its methods are synchronized, so individual map operations are synchronized, with synchronization overhead. HashMap was introduced with the Collections Framework in Java 1.2, is not synchronized, and generally has less overhead in non-concurrent use. HashMap allows one null key and multiple null values, while Hashtable allows neither. Neither guarantees ordering. For modern concurrent code, I would normally consider ConcurrentHashMap rather than Hashtable.”

Hashtable predates the Collections Framework. It came from Java 1.0. When the Collections Framework arrived in Java 1.2, HashMap was designed as part of the modern Map hierarchy. Hashtable was later made to implement Map, but retained its legacy design.

5. Thread safety — the important nuance

Hashtable

Methods such as put(), get() and remove() are synchronized.

Hashtable<String,Integer> h = new Hashtable<>();
h.put("A", 10); // synchronized
h.get("A");     // synchronized

HashMap

It does not synchronize access.

HashMap<String,Integer> h = new HashMap<>();
h.put("A", 10); // not synchronized
h.get("A");     // not synchronized
Very important: “Hashtable is thread-safe” does not mean every multi-step business operation is automatically atomic.

if (!map.containsKey(k)) map.put(k,v) is a compound operation. Synchronizing the individual calls does not automatically make the entire sequence atomic.

If the interviewer asks, “If Hashtable is thread-safe, why not use it?”, a strong answer is:

“Hashtable is legacy. For modern concurrent applications, ConcurrentHashMap is generally the better choice because it is designed specifically for concurrent access and provides concurrency-oriented operations.”

7. Null handling — easy interview marks

HashMap ✓

Map<String,Integer> map = new HashMap<>();
map.put(null, 100); // OK
map.put("A", null); // OK
map.put("B", null); // OK

One null key and multiple null values.

Hashtable ✗

Hashtable<String,Integer> h = new Hashtable<>();
h.put(null, 100); // NullPointerException
h.put("A", null); // NullPointerException

Neither null keys nor null values are allowed.

8. Ordering — common trap

Neither HashMap nor Hashtable guarantees insertion order.

  • Insertion order → LinkedHashMap
  • Sorted keys → TreeMap
  • Concurrent access → ConcurrentHashMap

9. Internal concepts

Hashing

A key's hashCode() participates in locating the entry.

Collision

Different keys can map to the same bucket, so collisions must be handled.

equals()

After a hash collision, equality is important for determining whether keys are actually equal.

Modern HashMap detail: In current JDK implementations, heavily-collided buckets can be treeified under certain conditions. You may hear this described as tree bins. This is a useful senior-level HashMap detail, but avoid presenting JDK implementation details as universal API guarantees.

10. Capacity & load factor

Both use hashing and have concepts such as capacity and load factor. The load factor helps determine when the table should grow and entries be redistributed.

HashMap<String,Integer> map = new HashMap<>(16, 0.75f);
Hashtable<String,Integer> table = new Hashtable<>(16, 0.75f);

For interviews, understand the concept; don't over-focus on JDK-specific implementation details unless asked.

12. Fail-fast example

Map<String,Integer> map = new HashMap<>();
map.put("A", 1);
map.put("B", 2);

for (String key : map.keySet()) {
    map.put("C", 3); // structural modification
}

This can cause ConcurrentModificationException. Fail-fast behavior is not a thread-safety mechanism.

14. Interview follow-up ladder

Q1. Main difference?
Hashtable is legacy and synchronized; HashMap is part of the modern Collections Framework and is not synchronized.
Q2. Can HashMap contain null?
Yes — one null key and multiple null values.
Q3. Can Hashtable contain null?
No — neither null keys nor null values.
Q4. Is HashMap thread-safe?
No.
Q5. Is Hashtable thread-safe?
Its legacy map methods are synchronized, but multi-operation workflows still need appropriate coordination.
Q6. Thread-safe map today?
Usually consider ConcurrentHashMap, depending on the requirements.
Q7. Which preserves insertion order?
Neither. Use LinkedHashMap.
Q8. Which is faster?
HashMap generally has less synchronization overhead in non-concurrent use. Avoid claiming an absolute result without a benchmark/workload.
Q9. Why no null in Hashtable?
It is a legacy design choice; null keys and values are rejected.
Q10. HashMap vs ConcurrentHashMap?
ConcurrentHashMap is specifically designed for concurrent access and includes useful atomic-style operations such as putIfAbsent() and computeIfAbsent().

15. What a senior QA/SDET answer should sound like

Don't stop at “Hashtable is synchronized and HashMap isn't.” Connect the ideas:

  1. History: Hashtable is Java 1.0 legacy; HashMap came with Collections Framework in Java 1.2.
  2. Design: Hashtable extends Dictionary; HashMap extends AbstractMap and participates naturally in the Map hierarchy.
  3. Behavior: HashMap allows null; Hashtable doesn't.
  4. Concurrency: Hashtable synchronizes legacy map methods; HashMap doesn't.
  5. Ordering: Neither guarantees insertion order.
  6. Modern choice: HashMap for normal use; ConcurrentHashMap for many concurrent use cases.
