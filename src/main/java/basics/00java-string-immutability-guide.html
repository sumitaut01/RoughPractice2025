1. What "immutable" actually means

Once a String object is created, its internal character data can never be changed. Every method that looks like it "modifies" a string — toUpperCase(), replace(), concat(), substring() — actually returns a brand-new String object, leaving the original untouched.

String s = "sumit";
s.toUpperCase();       // return value is thrown away here!
System.out.println(s); // still prints "sumit"

s = s.toUpperCase();   // NOW s points to the new object
System.out.println(s); // prints "SUMIT"
Calling a String method without reassigning the result does nothing observable. This is one of the most common beginner (and tired-senior-dev-at-11pm) bugs.

2. Why String was designed immutable

  • String pool reuse — safe to share one object across many references only if nobody can mutate it underneath another reference.
  • Thread safety — immutable objects are automatically safe to share across threads, no synchronization needed.
  • Security — class loaders, file paths, network connections, DB URLs are passed as Strings. If String were mutable, code could change a value after a security check but before it's used (a classic TOCTOU bug).
  • Hashcode caching — since the content can never change, hashCode() can be computed once and cached, making Strings very fast as HashMap keys.

3. The String Constant Pool (SCP)

The JVM keeps a special memory region (part of the heap since Java 7) called the String Constant Pool. Any string literal written directly in code is placed there, and the JVM reuses an existing entry rather than creating a duplicate.

String s1 = "sumit"; String s2 = "sumit"; Heap ┌───────────────────────────────┐ │ String Constant Pool │ │ ┌───────────┐ │ │ │ "sumit" │ <── s1 │ │ └───────────┘ <── s2 (same!)│ └───────────────────────────────┘

Both s1 and s2 point to the same object in the pool, so s1 == s2 is true.

In automation frameworks (Selenium page objects, config loaders) people sometimes build config keys with new String() and then use == for comparison somewhere downstream — an intermittent, hard-to-reproduce bug because it "works" for pooled strings and silently fails for these.

5. == vs .equals()

  • == compares references (memory identity) for objects — it's asking "are these literally the same object?"
  • .equals() (overridden in String) compares content, character by character.
Never use == to compare Strings in test assertions or business logic — only use it when you deliberately want reference identity (rare). In TestNG/JUnit, Assert.assertEquals(actual, expected) already uses .equals() under the hood — good — but a raw if (status == "PASSED") in helper code is a landmine.

6. System.identityHashCode()

identityHashCode() returns the JVM's default hash code (based on the object's memory identity), ignoring any overridden hashCode(). This is the tool to actually prove two references point to the same object vs. two equal-but-distinct objects.

String s  = "sumit";
String ss = new String("sumit");

System.out.println(s.hashCode());                 // same value for both (content-based)
System.out.println(ss.hashCode());                 // same value for both (content-based)

System.out.println(System.identityHashCode(s));   // different
System.out.println(System.identityHashCode(ss));  // different
hashCode() can be equal for two different objects (it's content-based and even allows collisions by design), but identityHashCode() being equal is a much stronger guarantee — for two ordinary objects it effectively means == would be true.

7. intern()

Manually places a string's content into the pool (or returns the existing pooled entry if it's already there), and returns that pooled reference.

String ss = new String("sumit");
String pooled = ss.intern();

System.out.println(ss == pooled);        // false
System.out.println("sumit" == pooled);   // true
Overusing intern() on high-cardinality, runtime-generated strings (e.g. dynamic test data, UUIDs) can bloat the pool and cause GC/perf issues in long-running processes — it was a known problem before Java 7 moved the pool into the regular garbage-collected heap.

8. Concatenation gotchas

String a = "sum" + "it";        // compile-time constant -> pooled, same as "sumit" literal
String b = "sumit";
System.out.println(a == b);      // true! javac folds literal + literal at compile time

String part = "sum";
String c = part + "it";          // NOT a compile-time constant (part is a variable)
System.out.println(c == b);      // false — built at runtime via StringBuilder

final String part2 = "sum";      // final + literal IS a compile-time constant
String d = part2 + "it";
System.out.println(d == b);      // true again!
Whether concatenation is resolved at compile time depends on whether every operand is a final compile-time constant. Adding just one non-final variable flips the whole expression to runtime evaluation (internally rewritten as new StringBuilder().append(...).toString()), which never touches the pool.
Concatenating Strings with + inside a loop creates a new StringBuilder (and discards it) on every iteration in older javac versions — O(n²) behavior. Always use an explicit StringBuilder for loop-based concatenation, especially when building large log/report strings in test frameworks.

9. substring() memory history pre-Java 7u6 vs modern

Before Java 7 update 6, substring() shared the original character array — the substring object held a reference to the same backing char[] as the original string, just with different offset/length fields. This meant a tiny substring of a huge string kept the entire huge array alive in memory.

Pre Java 7u6: bigString.substring(0,3) --> shares char[] with bigString (memory leak risk) Java 7u6+: substring() --> copies only the needed characters into a new char[] (Arrays.copyOfRange)
This is largely historical now (fixed since 2012), but it still shows up in interviews and in legacy JDK 6 codebases. If you ever see advice to "manually copy substrings with new String(s.substring(...)) to avoid memory leaks," that advice is a relic of pre-7u6 Java.

10. Cached hashCode()

String caches its computed hash code in a private int hash field after the first call, since immutability guarantees it will never change. This is exactly why Strings are efficient as HashMap/HashSet keys — repeated lookups don't recompute the hash.

This caching is a direct consequence of immutability — it's a good talking point that ties "why immutable" back to "what concrete benefit does it give me."

11. Breaking immutability via reflection don't do this in prod

Immutability is a language-level contract, not an absolute physical guarantee. Using reflection, it's historically been possible to reach into a String's private backing array and mutate it — because pooled strings are shared, this can corrupt every reference to that literal across the entire JVM.

Modern JDKs (9+) increasingly restrict this via the module system and strong encapsulation (--illegal-access changes, JEP 396/403), but it remains a favorite "immutability isn't magic" interview gotcha. The practical lesson: immutability is enforced by the class's public API, not by the JVM making mutation physically impossible.

12. Why passwords should be char[], not String

  • A password stored as String may live in the pool (or heap) for an indeterminate time — you cannot force-clear it, since Strings are immutable and there's no public API to zero out the contents.
  • It may get swapped to disk, appear in heap dumps, or linger for GC cycles.
  • A char[] can be explicitly overwritten (Arrays.fill(pwd, '0')) the moment it's no longer needed.
JPasswordField.getPassword() in Swing intentionally returns char[], not String, for exactly this reason. Same logic applies to any secrets/tokens read in automation frameworks (e.g. reading credentials from a config file for a Selenium login test) — don't leave them as long-lived Strings if you can avoid it.

13. String in switch

Java compiles a switch on Strings using hashCode() for the initial bucket, then falls back to .equals() to confirm the match (guarding against hash collisions). It never uses == internally, so it works correctly regardless of pooling.

14. final fields & compile-time constants

final String BASE = "https://x4v";
final String FULL = BASE + "/unite";   // compile-time constant -> pooled

String base2 = "https://x4v";          // not final
String full2 = base2 + "/unite";       // runtime concatenation -> NOT pooled

System.out.println(FULL == "https://x4v/unite"); // true
System.out.println(full2 == "https://x4v/unite"); // false
A common misconception: people assume any concatenation of "clearly fixed-looking" strings is pooled. It's only pooled if the compiler can prove it's a constant — which requires every part to be either a literal or a final variable initialized with a constant expression.

15. Related gotcha: Integer caching (not String, but same shape of bug)

Integer i1 = 100;
Integer i2 = 100;
System.out.println(i1 == i2);  // true  (cached, -128 to 127)

Integer i3 = 200;
Integer i4 = 200;
System.out.println(i3 == i4);  // false (outside cache range)
Not about String directly, but it's the exact same class of "pooling makes == behave inconsistently" bug, so it tends to appear right after String pool discussions in interviews and in real code (flaky assertions that pass for small numbers and fail for large ones).
