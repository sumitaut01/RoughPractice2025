1. The core difference

A monolith is one deployable app — even if it's internally layered, all its modules run in the same process and share the same database. A microservices system is many independently deployable services that talk to each other over the network (usually REST/HTTP or messaging), each owning its own data.

That single fact — shared process vs. network boundary — is what decides which testing tool you reach for.

Monolith

  • One codebase, one deployment
  • In-process calls between modules
  • One shared database/transaction
  • Integration test = spin up the app, hit its REST API
  • Tool of choice: RestAssured (+ TestNG/JUnit)

Microservices

  • Many codebases, many deployments
  • Network calls between services
  • Each service owns its own DB
  • Integration test = does every consumer/provider pair agree on the API shape?
  • Tool of choice: Pact-JVM (contract testing) + RestAssured per-service
Key insight: RestAssured doesn't go away in microservices — you still use it to test each service's own REST API in isolation. What changes is how you test the connections between services. Spinning up all real services for every test run doesn't scale, so you replace "real integration" with "contract testing."

2. Testing a monolith with RestAssured

In a monolith, integration testing is straightforward: start the whole app (in-memory or on a test port), then drive its REST endpoints exactly like a real client would. RestAssured is built for exactly this — fluent given/when/then syntax, JSON path assertions, schema validation.

Example context: imagine X4V Unite was still a single monolith exposing both order placement and pricing calculation from one app. A test would create an order and assert the final price came back correct — all in one HTTP call, one process, one DB transaction.
@Test
public void shouldReturnDiscountedPrice_whenBulkOrderPlaced() {
    given()
        .baseUri("http://localhost:8080")
        .contentType("application/json")
        .body("""
            {
              "customerId": "CUST-1042",
              "items": [ { "sku": "X4V-PUMP-200", "qty": 12 } ]
            }
            """)
    .when()
        .post("/orders")
    .then()
        .statusCode(201)
        .body("pricing.ruleApplied", equalTo("BULK_DISCOUNT_TIER_2"))
        .body("pricing.finalUnitPrice", lessThan(100.0f))
        .body("orderStatus", equalTo("CONFIRMED"));
}

One test, one process, real DB — because in a monolith, "order placement" and "pricing calculation" live in the same deployable. There's no network boundary to worry about, so a straight end-to-end assertion is cheap and reliable.

3. Testing microservices with Pact-JVM

Once pricing splits out into its own service — say, X4VPricingEngine — and OrderService calls it over HTTP, a full end-to-end test now needs both services running, both databases seeded, and network calls that can flake. Multiply that by every consumer of every service, and full integration testing stops scaling.

Contract testing solves this by testing each side against a shared "contract" (a pact file) instead of against each other directly:

OrderService
(consumer)
— writes expectations →
pact.json
(the contract)
— verified against →
X4VPricingEngine
(provider)

3a. Consumer test — OrderService defines what it expects

OrderService runs against a mock of X4VPricingEngine, generated by Pact-JVM. If the mock returns what OrderService expects, Pact records the interaction into a pact file.

@Test
public void consumerTest_getPricingForSku(MockServer mockServer) {

    RequestResponsePact pact = ConsumerPactBuilder
        .consumer("OrderService")
        .hasPactWith("X4VPricingEngine")
        .given("SKU X4V-PUMP-200 has an active bulk discount rule")
        .uponReceiving("a request for pricing on a bulk quantity")
            .path("/pricing/calculate")
            .method("POST")
            .body("{ \"sku\": \"X4V-PUMP-200\", \"qty\": 12 }")
        .willRespondWith()
            .status(200)
            .body("{ \"finalUnitPrice\": 92.50, \"ruleApplied\": \"BULK_DISCOUNT_TIER_2\" }")
        .toPact();

    // call OrderService's client code against the Pact mock server,
    // assert it parses the response correctly — this ALSO writes the pact file
}

3b. Provider verification — X4VPricingEngine proves it honors the contract

On the provider side, Pact-JVM replays every recorded interaction from the pact file against the real X4VPricingEngine (with test data seeded per the given() state) and checks the real response matches what was promised.

@Provider("X4VPricingEngine")
@PactFolder("pacts")
public class PricingEngineProviderTest {

    @State("SKU X4V-PUMP-200 has an active bulk discount rule")
    public void seedBulkDiscountRule() {
        // insert the pricing rule row the interaction assumes exists
        ruleRepository.save(new PricingRule("X4V-PUMP-200", "BULK_DISCOUNT_TIER_2", 12));
    }

    @TestTemplate
    @ExtendWith(PactVerificationInvocationContextProvider.class)
    void pactVerificationTestTemplate(PactVerificationContext context) {
        context.verifyInteraction();
    }
}

Neither side ever calls the other over a live network during CI. Each runs independently, both stay honest against the same pact file — and if X4VPricingEngine ever changes its response shape, provider verification fails immediately, before it ever reaches a real integration environment.

4. Putting it together — your OrderService / X4VPricingEngine setup

This maps directly onto the split you're already building:

LayerWhat's testedTool
X4VPricingEngine's own REST API Does /pricing/calculate correctly apply the ~30 ranked rules for a given payload? RestAssured
OrderService's own REST API Does /orders correctly create, validate, persist an order? RestAssured
OrderService ⇄ X4VPricingEngine contract Does OrderService send what X4VPricingEngine expects, and does X4VPricingEngine return what OrderService expects — without running both together? Pact-JVM

In practice this gives you three levels of confidence stacked on top of each other, each one cheap to run and fast to fail:

  1. Unit/API tests per service (RestAssured) — fast, no cross-service dependency
  2. Contract tests (Pact-JVM) — catch breaking changes between OrderService and X4VPricingEngine in CI, before deployment
  3. A thin layer of real end-to-end tests (RestAssured against both services live) — kept small, reserved for the handful of critical business flows, since it's the slowest and flakiest layer

5. When to use which

SituationUse
Testing one service/app's own endpoints, DB, business logicRestAssured
Verifying two independently-deployed services agree on a request/response shapePact-JVM
Confirming a full user journey works across several live services (rare, expensive)RestAssured, run end-to-end, kept minimal
Catching a breaking API change before it reaches stagingPact-JVM provider verification in CI
Rule of thumb: if two things are built and deployed together, test them together with RestAssured. If they're built and deployed separately, test the connection between them with Pact-JVM — and test each one's own behavior with RestAssured.
