01 — Core idea

Why it's trending

Instead of pointing tests at a shared staging DB — which drifts, gets dirty, or is simply down when you need it — Testcontainers spins up a real instance of that dependency in Docker, runs your tests against it, then discards it.

Every test run gets a clean, isolated, fully reproducible environment. No shared state between runs, no "works on my machine," no coordinating with whoever else is using the staging DB.

03 — Database container

Your highest-value entry point

Since you already work with PostgreSQL and Oracle in your DB layer, this is where Testcontainers pays off fastest: your test setup stops depending on a shared instance being reachable, seeded, or clean.

OrderRepositoryTest.java
public class OrderRepositoryTest {

    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine")
            .withDatabaseName("testdb")
            .withUsername("test")
            .withPassword("test");

    @BeforeClass
    public void startContainer() {
        postgres.start();
        System.setProperty("db.url", postgres.getJdbcUrl());
        System.setProperty("db.user", postgres.getUsername());
        System.setProperty("db.password", postgres.getPassword());
    }

    @AfterClass
    public void stopContainer() {
        postgres.stop();
    }

    @Test
    public void testOrderPersistence() {
        // your existing JDBC/DAO code connects using db.url above
    }
}
Oracle note

Oracle's official image isn't freely licensed the same way Postgres is — use gvenzl/oracle-free:23-slim instead: new OracleContainer("gvenzl/oracle-free:23-slim").withDatabaseName("testdb")

04 — Selenium container

Your existing tests, unchanged

Runs a real browser inside a container. Your Page Object code doesn't change — only where the browser lives.

LoginTest.java
public class LoginTest {

    static BrowserWebDriverContainer<?> chrome =
        new BrowserWebDriverContainer<>()
            .withCapabilities(new ChromeOptions());

    @BeforeClass
    public void startBrowser() {
        chrome.start();
    }

    @Test
    public void testLogin() {
        RemoteWebDriver driver = new RemoteWebDriver(chrome.getSeleniumAddress(), new ChromeOptions());
        driver.get("https://your-app-under-test");
        // existing Selenium Page Object code works unchanged here
        driver.quit();
    }
}

05 — Framework fit

Wiring it into your hybrid framework

You already run Selenium + API + DB together with ThreadLocal-based parallelism. The natural integration point is your suite-level lifecycle hooks:

  • @BeforeSuite — start shared containers (DB, maybe a mock API server via MockServer or WireMock) once
  • Config layer — inject the dynamic JDBC URL / port into the same place your multi-country YAML config resolves baseUri per environment, instead of a static property
  • @AfterSuite — stop containers

This leaves your reusable ApiResponseWrapper<T>, ResponseValidator<T>, and GenericDataProvider components untouched — Testcontainers only changes where the DB/browser lives, not how your framework talks to them.

06 — Key concepts

Worth knowing before you build

SINGLETON CONTAINER

Starting one container per test class is often wasteful. A shared static container across a suite — started once, reused — is the common production pattern for speed.

TESTNG LIFECYCLE

@Testcontainers + @Container are JUnit 5 annotations. For TestNG, manage lifecycle manually via @BeforeSuite/@BeforeClass — the testcontainers-testng module gives similar helpers.

WAIT STRATEGIES

waitingFor(Wait.forHttp("/health")) ensures tests don't start before the service inside the container is actually ready.

LOCAL REUSE

Set testcontainers.reuse.enable=true in ~/.testcontainers.properties to avoid recreating containers on every local run. Don't enable this on CI.

07 — Where it fits

What it replaces — and what it doesn't

DOESN'T REPLACE

RestAssured or Selenium — it changes where the target service lives for testing, not how your framework talks to it.

BIGGEST WIN

Your DB-layer tests become fully self-contained — no shared Postgres/Oracle instance to coordinate — and CI runs become more reproducible.

OPTIONAL

Selenium-in-container is mainly a "no Grid needed" convenience. If you already run Grid or cloud infra, this part is optional.
