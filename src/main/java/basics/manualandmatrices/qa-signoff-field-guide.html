01 — What metrics to report after sprint testing

"Testing is over" isn't a feeling — it's a set of numbers against agreed exit criteria. These are the numbers people are actually asking for, whether they know it or not.

Coverage metrics

  • Requirement / story coverage — % of committed stories with at least one mapped test case.
  • Test case execution coverage — executed ÷ planned.
  • Automation coverage — % of the regression suite that runs unattended, and separately, % of this sprint's new scenarios automated.
  • Risk coverage — % of pre-identified high-risk areas actually exercised (not just "tested," but tested with boundary/negative data).

Execution metrics

  • Planned vs Executed vs Passed vs Failed vs Blocked vs Not Run — as counts and percentages.
  • Pass rate trend across the sprint (day-1 pass % vs day-5 pass % tells you whether quality stabilized or the build kept regressing).

Defect metrics

  • Defects by severity/priority — Critical / High / Medium / Low, new vs carried over.
  • Defect density — defects per module, per story point, or per 100 test cases.
  • Defect rejection rate — % raised as "not a bug" / duplicate / can't-reproduce.
  • Reopen rate — % of "fixed" defects that failed retest.
  • Defect leakage rate — bugs found in prod ÷ (bugs found in prod + bugs found in test), for the previous release. This is the number that answers "how good was our testing," and it's the one people conflate with "did you sign off wrong."

Automation health

  • Suite execution time, pass rate, and flaky test % (tests that pass/fail non-deterministically — a high flaky rate quietly erodes trust in every other number on this list).
  • Script maintenance load — how many scripts broke due to app changes vs genuine defects caught.

Environment & data stability

  • Environment downtime hours during the sprint, and how many test cycles they cost.
  • Test data readiness — % of required data combinations actually available in the test environment.

This is the block people mean when they ask "what metrics did you send." Send it every sprint, in the same format, even when nobody asks — it's what makes the eventual "but you signed off" conversation a two-line reply instead of a scramble.

02 — A bug reached prod after signoff. What's the justification?

Signoff is not a promise of zero defects. It's a documented, risk-based decision that testing met an agreed exit criteria within known constraints. The justification is about restating that scope — not defending your competence.

The core argument

"Signoff certifies that testing was completed against the agreed scope and exit criteria, and that known residual risk was reviewed and accepted by stakeholders at that time. It is not a warranty against scenarios that fell outside that scope." Every justification below is a specific way of showing where the escaped defect sat relative to that scope.

Escaped-defect categories — pick the one that actually fits

CategoryWhat it means
Out-of-scope combinationA data/config combination that existed but wasn't in the test matrix because it wasn't flagged as in-scope or high-risk.
Requirement gapThe behavior was never specified, so no test case could have existed for it.
Environment/data mismatchTest environment or test data didn't mirror prod closely enough to expose the issue (config drift, third-party stub vs real service, data volume).
Timing / load-dependentRace condition, concurrency, or scale issue only reproducible under real production load.
Post-signoff changeConfig, data, or a dependent service changed in prod after signoff was given.
Accepted known riskThe item was actually known and logged at signoff, with stakeholder sign-off to ship anyway.

How to structure the justification

  • 1. State the exit criteria that was actually met — e.g. "All P1/P2 defects closed, 100% of committed story coverage, 68% automation coverage — all criteria in the sprint DoD were satisfied at signoff."
  • 2. Name the category from the table above. This is the single most important line — it turns "we missed it" into "here is precisely why it wasn't visible to the process that existed."
  • 3. Show the evidence — the test data set used, the requirement doc, the environment diff — whatever proves the gap was structural, not neglect.
  • 4. Convert it into a corrective action immediately, in the same breath. A justification without a fix attached reads as an excuse; one with a fix attached reads as ownership.
Real-time example — X4V Unite discount-rule rounding defect

What happened: Two sprints after signoff, a rounding error surfaced in production for orders using a fractional quantity combined with a specific currency conversion path in the rule engine.

Justification given: "At signoff, all 142 planned test cases covering the documented discount-rule requirements passed, including the standard boundary set (0, 1, max qty, whole-currency). The fractional-quantity + currency-conversion combination was never listed in the requirement spec or the risk register, so it wasn't part of the committed test matrix — this is an out-of-scope combination / requirement gap, not a missed execution of an existing case."

Immediate corrective action attached: Test data matrix for the rule engine expanded to include fractional-quantity × multi-currency combinations; requirement template updated so the BA must call out numeric edge cases explicitly going forward.

03 — Root cause analysis for an escaped defect

Two tools, used together: 5 Whys to drill from symptom to structural cause, and a fishbone to classify it once you get there. The output is never "someone missed it" — it's a bucket plus a preventive action.

Step-by-step method

1

Reproduce & isolate

Confirm the defect, pin the exact input/data/config that triggers it.

2

Reconstruct the timeline

When was it introduced (which build/commit), when should it have been caught (which test phase), why wasn't it.

3

Run the 5 Whys

Keep asking "why" until you hit a process/system cause, not a person.

4

Classify the root cause bucket

Requirement gap · Coverage/test-design gap · Test data gap · Environment gap · Process/schedule gap · Tooling/automation gap.

5

Define CAPA

Corrective action (fix this defect + backfill the test case) and Preventive action (fix the process so the class of defect can't recur silently).

6

Log it

Add to the defect-leakage log so it feeds next sprint's leakage-rate metric — the RCA should visibly move a number, not just live in a doc.

Fishbone categories for software RCA

People / Process

No exploratory session scheduled, review skipped, DoD not enforced.

Requirements / Design

Edge case never specified, ambiguous acceptance criteria.

Test Data

Data set didn't include the combination, no prod-like data available.

Environment / Tools

Config drift from prod, third-party mock instead of real integration.

Real-time example — 5 Whys on the X4V Unite rounding defect
Q1

Why did the bug reach production?

The rounding logic failed for a fractional-quantity + currency-conversion combination.

Q2

Why wasn't it caught in testing?

The test data set for the rule engine didn't include that combination.

Q3

Why wasn't that combination in the test data?

The requirement document never called out fractional-quantity edge cases.

Q4

Why didn't test design catch the gap independently?

Test cases were derived strictly from documented requirements; no exploratory/boundary session was scheduled for this rule-engine change.

Q5

Why was no exploratory session scheduled?

The sprint plan didn't allocate time for exploratory testing on pricing/rule-engine changes specifically.

Root cause bucket: Requirement gap + Process/schedule gap.

CAPA: (Corrective) Fix rounding logic, backfill regression case, hotfix release. (Preventive) Mandatory exploratory testing checklist for any rule-engine change; requirement template now requires the BA to specify numeric edge-case behavior; expanded boundary test-data matrix committed to the regression suite.

04 — What the end-of-day / sprint test report should look like

One document, same structure every time, so a reader can find the number they need in ten seconds without asking you for it.

  • Executive snapshot — sprint/build number, one-line overall status (Green / Amber / Red), one-line headline of what changed since last report.
  • Scope covered — modules/features tested this cycle, explicitly listing anything out of scope and why.
  • Execution summary — planned / executed / passed / failed / blocked, as counts and %.
  • Defect summary — by severity, new vs carried forward, defect density, leakage from the prior release if known.
  • Automation status — scripts run, pass rate, coverage %, flaky-test count.
  • Risks & open issues — anything known and accepted, environment blockers, dependencies not yet available.
  • Exit criteria checklist — each DoD item, met/not met, with a named sign-off for any waiver.
  • Recommendation — Go / No-Go / Go-with-conditions, stated as a single explicit line, not implied.
  • Appendix — links to the full defect list and test case set, for anyone who wants to go one level deeper.
