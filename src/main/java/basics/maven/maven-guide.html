1What is the use of Maven?

Maven is a build automation and project management tool for Java projects (though it can handle other JVM languages too). Instead of everyone on a team compiling, testing, and packaging code by hand with custom scripts, Maven standardizes the whole process using one file: pom.xml (Project Object Model).

Concretely, Maven is used for:

  • Dependency management — declare libraries (e.g. TestNG, RestAssured, Selenium) in pom.xml and Maven downloads them (and their transitive dependencies) from a repository like Maven Central, instead of you manually hunting for JARs.
  • Standard build lifecycle — every Maven project follows the same phases: validate → compile → test → package → verify → install → deploy. Anyone who knows Maven can build any Maven project the same way.
  • Consistent project structure — src/main/java, src/test/java, src/main/resources, etc. This "convention over configuration" means less setup per project.
  • Packaging — produces the final artifact: JAR, WAR, EAR, etc.
  • Running tests as part of the build — e.g. TestNG/JUnit suites run automatically via the Surefire plugin during the test phase — directly relevant to test-automation frameworks.
  • Reproducible builds across machines/CI — the same pom.xml builds identically on a developer's laptop and on Jenkins/GitHub Actions.
In short: Maven answers "what libraries do I need, how do I compile/test/package this project, and how do I do it the same way every time, on every machine?"

2Using variables in Maven (Properties)

In Maven, "variables" are called properties. They're defined inside the <properties> block of pom.xml and referenced anywhere else using ${propertyName} syntax.

Defining a property

<project>
    ...
    <properties>
        <java.version>17</java.version>
        <selenium.version>4.22.0</selenium.version>
        <testng.version>7.10.2</testng.version>
        <env>qa</env>
    </properties>
</project>

Referencing a property

<dependencies>
    <dependency>
        <groupId>org.seleniumhq.selenium</groupId>
        <artifactId>selenium-java</artifactId>
        <version>${selenium.version}</version>
    </dependency>
    <dependency>
        <groupId>org.testng</groupId>
        <artifactId>testng</artifactId>
        <version>${testng.version}</version>
    </dependency>
</dependencies>

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <configuration>
                <source>${java.version}</source>
                <target>${java.version}</target>
            </configuration>
        </plugin>
    </plugins>
</build>

This means when Selenium releases a new version, you change it in one place instead of hunting through the whole POM.

Kinds of built-in / implicit properties

PropertyMeaning
${project.version}The version of the project itself (from <version> tag)
${project.basedir}Root directory of the project
${settings.localRepository}Path to local .m2 repo
${env.SOME_VAR}Reads an OS environment variable, e.g. ${env.PATH}

3Maven Profiles

A profile is a named, optional set of configuration (properties, dependencies, plugins) that only gets applied when that profile is activated. This is exactly how test frameworks typically switch between environments — QA, Staging, Prod — or between browsers, without duplicating the whole POM.

Defining profiles

<project>
    ...
    <profiles>
        <profile>
            <id>qa</id>
            <properties>
                <base.url>https://qa.example.com</base.url>
                <db.host>qa-db.internal</db.host>
            </properties>
        </profile>

        <profile>
            <id>staging</id>
            <properties>
                <base.url>https://staging.example.com</base.url>
                <db.host>staging-db.internal</db.host>
            </properties>
        </profile>

        <profile>
            <id>prod</id>
            <activation>
                <activeByDefault>false</activeByDefault>
            </activation>
            <properties>
                <base.url>https://prod.example.com</base.url>
            </properties>
        </profile>
    </profiles>
</project>

Ways a profile can activate

  • Explicitly via CLI — mvn test -Pqa
  • By default — <activeByDefault>true</activeByDefault>, runs when no other profile is specified
  • By JDK version — <jdk>17</jdk> inside <activation>
  • By OS — <os><family>windows</family></os>
  • By presence of a system property — <property><name>env</name></property>
  • By a file's existence/absence — useful to auto-detect local vs CI setups

A profile can also add/override <dependencies>, <plugins>, or <build> config — not just properties.

4Consuming / passing variables from the command line

1. Passing a system property directly with -D

You can inject or override a property value at runtime with -D, without touching the POM:

mvn test -Dbrowser=chrome -Denv=qa

Inside your Java/TestNG code, you'd read it as:

String browser = System.getProperty("browser", "chrome"); // default fallback

Inside pom.xml, that same value is accessible as ${browser}, and you can even wire it into the Surefire plugin so it's forwarded into the JVM running your tests:

<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-surefire-plugin</artifactId>
    <configuration>
        <systemPropertyVariables>
            <browser>${browser}</browser>
            <env>${env}</env>
        </systemPropertyVariables>
    </configuration>
</plugin>

2. Activating a profile with -P

mvn clean test -Pstaging

This activates the staging profile block shown earlier, pulling in whatever properties/dependencies/plugins it defines — e.g. ${base.url} now resolves to the staging URL for that run.

3. Combining profile + override together

mvn clean test -Pqa -Dbrowser=firefox -DsuiteXmlFile=testng-smoke.xml
Precedence tip: a value passed with -D on the command line overrides the same-named property defined inside <properties> in the POM (including inside an active profile). This is exactly why -D is the standard way CI pipelines override environment/browser/suite per run.

4. Passing a whole TestNG suite file dynamically

mvn test -DsuiteXmlFile=testng-regression.xml
<plugin>
    <artifactId>maven-surefire-plugin</artifactId>
    <configuration>
        <suiteXmlFiles>
            <suiteXmlFile>${suiteXmlFile}</suiteXmlFile>
        </suiteXmlFiles>
    </configuration>
</plugin>

5Role of a plugin in Maven

Maven's core itself does very little — almost everything it "does" (compiling, testing, packaging, code coverage, static analysis) is actually performed by plugins. A plugin is a collection of goals (individual tasks) that get bound to phases of the build lifecycle.

Common plugins and what they do

PluginRole
maven-compiler-pluginCompiles .java source files into .class bytecode
maven-surefire-pluginRuns unit/integration tests (TestNG/JUnit) during the test phase
maven-failsafe-pluginRuns integration tests during verify, separate from unit tests
maven-jar-plugin / maven-war-pluginPackages compiled classes into a JAR/WAR
maven-shade-pluginBuilds an "uber/fat" JAR with all dependencies bundled in
maven-site-pluginGenerates project documentation/reports as a website
allure-mavenGenerates Allure test reports (common in automation frameworks)

How a plugin goal gets triggered

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-surefire-plugin</artifactId>
            <version>3.2.5</version>
            <executions>
                <execution>
                    <phase>test</phase>
                    <goals>
                        <goal>test</goal>
                    </goals>
                </execution>
            </executions>
        </plugin>
    </plugins>
</build>

You can also invoke a plugin goal directly without running a full lifecycle phase:

mvn org.apache.maven.plugins:maven-dependency-plugin:tree
Think of it this way: pom.xml is the "what to build" — plugins are the "how it's actually done." Maven core just orchestrates when each plugin goal fires.

6Plugin dependency vs. regular project dependency

This is a common point of confusion, so here's the distinction clearly:

  Dependency Plugin Dependency
Declared under <project><dependencies> <plugin><dependencies> (nested inside a specific plugin)
Purpose Adds a library to your project's compile/test/runtime classpath — code you write can import and use it directly Adds a library to the plugin's own classpath so the plugin itself can use it while it executes — your application code never sees it
Example use case Adding Selenium, RestAssured, or TestNG so your test classes can call their APIs Adding a specific TestNG version to maven-surefire-plugin so Surefire knows how to discover/run TestNG tests with that exact version, independent of what's on your app classpath
Scope of effect Affects compiling/running your source code Affects only how that one plugin behaves during its execution

Regular dependency (for your code)

<dependencies>
    <dependency>
        <groupId>io.rest-assured</groupId>
        <artifactId>rest-assured</artifactId>
        <version>5.4.0</version>
        <scope>test</scope>
    </dependency>
</dependencies>

Plugin dependency (for the plugin's own execution)

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-surefire-plugin</artifactId>
            <version>3.2.5</version>
            <dependencies>
                <dependency>
                    <groupId>org.apache.maven.surefire</groupId>
                    <artifactId>surefire-testng</artifactId>
                    <version>3.2.5</version>
                </dependency>
            </dependencies>
        </plugin>
    </plugins>
</build>
Rule of thumb: if the library needs to be import-ed in your .java source files → it's a regular <dependencies> entry. If the library only helps a plugin do its job internally (a provider, an extra plugin capability, a specific runner integration) → it's a plugin dependency nested inside that <plugin> block.
