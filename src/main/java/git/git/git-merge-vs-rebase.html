02 — the non-negotiable

The one rule that matters more than preference

!

Never rebase a branch other people have already pulled from.

Rebase rewrites commits — new hashes, same content. Anyone with a copy of the old commits now has a history that has diverged from yours, and their next pull turns into a painful, duplicated mess. Merge is additive and safe on shared branches. Rebase is a local cleanup tool for history you alone own — right up until the moment you push it, after which it becomes public and immutable by the same rule.

04 — decision guide

So which one, when?

Reach for merge when…

  • You're integrating a shared or public branch — release branches, `main`, anything others have pulled
  • You want an honest record of when a feature actually landed, for audits or release notes
  • The feature branch is long-lived and you'd rather resolve conflicts once, at merge time
  • You need easy revertability — undoing a whole feature should be one command
  • Your team's workflow is PR-based with squash-and-merge or standard merge commits on GitHub/GitLab

Reach for rebase when…

  • You're cleaning up your own local branch before opening a pull request
  • You want to catch up with main mid-feature without a noisy merge commit cluttering the log
  • You're squashing or reordering messy WIP commits into a coherent, reviewable story (interactive rebase)
  • The team values a linear, bisectable history for `git bisect` and clean blame
  • The branch is yours alone and hasn't been pushed — or you've explicitly agreed force-pushes are OK

05 — quick reference

Commands you'll actually reach for

git merge feature
Merge feature into the current branch, creating a merge commit if histories diverged
git merge --no-ff feature
Force a merge commit even if a fast-forward were possible — keeps the feature's shape visible in history
git rebase main
Replay the current branch's commits on top of main's latest tip
git rebase -i HEAD~5
Interactive rebase — squash, reorder, reword, or drop the last 5 commits before sharing them
git rebase --abort
Bail out mid-rebase and return to the state before it started
git pull --rebase
Fetch and replay your local commits on top instead of creating a merge commit on pull
git push --force-with-lease
The only safe way to push a rebased branch — fails if someone else pushed in the meantime

merge preserves truth · rebase preserves narrative — pick the one your history needs
