GitHub Copilot Code Review — Setup & Custom Instructions

How Copilot shows up as a PR reviewer, and how to steer its feedback for our Selenium/Java stack.

1Why Copilot appears as a reviewer

Copilot code review is not on by default — it only appears on PRs because someone (a repo or org admin) explicitly enabled it. Once enabled, it behaves like an automated reviewer: it reads the PR diff and leaves inline comments and suggestions, the same way a human reviewer would.

It can be enabled in two ways:

ModeHow it works
Automatic A repo/org admin sets up a ruleset ("Automatically request Copilot code review") so Copilot is added to every new PR without anyone asking.
Manual Anyone can add "Copilot" in the PR's Reviewers list, the same way you'd request a human reviewer.
Check it yourself: Go to Repo → Settings → Rules → Rulesets and look for a rule referencing Copilot code review to see whether it's configured at the repo or org level.

2What rules Copilot follows

By default, Copilot reviews using its own general good-practice judgment — things like code smells, potential bugs, naming, and error handling. It has no awareness of our project-specific conventions unless we tell it.

We can steer it with a custom instructions file committed to the repo. Copilot reads this automatically on every review — no extra configuration needed once the file exists.

.github/copilot-instructions.md

3Our custom instructions file

Below is the version tailored to our Selenium + Java + TestNG + RestAssured framework. Trim any section that doesn't apply to a given repo.

# Copilot Code Review Instructions

This project is a **Selenium + Java + TestNG** UI automation framework, with
API testing via **RestAssured** and DB validation against **PostgreSQL/Oracle**.
Use the conventions below when reviewing pull requests.

## General Review Priorities

- Flag flaky-prone patterns before style nits — flakiness costs more than
  formatting.
- Prefer correctness and maintainability over cleverness. Test code should be
  boring and obvious to read.
- Call out anything that will break in CI (headless mode, parallel execution,
  environment-specific paths) even if it works locally.

## Selenium / UI Layer

- No hardcoded Thread.sleep() — flag it every time. Require explicit waits
  (WebDriverWait + ExpectedConditions) or a framework wait utility instead.
- Locators should prefer stable attributes (id, data-testid,
  name) over brittle XPath chains or CSS built on DOM position/index.
- Page Object classes should not contain assertions — assertions belong in
  test/step classes, not Page Objects.
- Driver instances must come from the framework's ThreadLocal driver
  manager — flag any direct new ChromeDriver() / new FirefoxDriver()
  instantiation inside test classes.
- No static WebDriver fields — breaks parallel execution.

## TestNG / Test Structure

- Every test method should have a clear, single responsibility — flag tests
  doing multiple unrelated validations under one @Test.
- Test methods must use descriptive names (behavior-based, e.g.
  shouldRejectLoginWithExpiredToken, not test1 or loginTest).
- Required TestNG annotations/attributes should be present where
  applicable: groups, priority (only when order truly matters), and
  description.
- Data-driven tests should use @DataProvider rather than duplicated test
  methods with hardcoded variants.
- No hard dependencies between independent test methods
  (dependsOnMethods should only be used for genuine setup chains, not to
  force ordering).

## API Layer (RestAssured)

- Response validation should use the framework's ResponseValidator /
  schema validation utilities rather than ad hoc assertEquals on raw
  JSON paths, where a validator already exists for that endpoint.
- Flag inline base URIs, tokens, or environment-specific values — these
  must come from the YAML/config-driven environment setup.
- Request/response logging should use existing Filters, not
  System.out.println debugging left in test code.

## Assertions & Reporting

- Use soft assertions (SoftAssert) when validating multiple independent
  fields in one test, so one failure doesn't mask the rest.
- Every assertion should have a clear failure message — flag bare
  assertEquals(a, b) with no message.
- No swallowed exceptions — flag empty catch blocks or
  catch (Exception e) {} with no logging/rethrow.

## Database Validation

- DB assertions should clean up any test data they insert (teardown in
  @AfterMethod/@AfterClass), unless intentionally shared fixture data.
- Flag raw SQL string concatenation with variables — require
  parameterized queries.

## Code Hygiene

- No commented-out code blocks — flag and request removal.
- No unused imports, unused variables, or dead code left from debugging.
- Secrets, tokens, or credentials must never be hardcoded — must come from
  config/environment/secrets manager.

## What NOT to flag

- Minor formatting differences already handled by the project's
  formatter/linter (don't duplicate what static analysis already covers).
- Naming style disagreements that don't affect readability (e.g. minor
  verb choice in method names) — keep these low priority, not blocking.

4Rollout notes

  • Commit the file at repo root under .github/copilot-instructions.md — no toggle or setting needs to be flipped to activate it.
  • Remove sections that don't apply to a given repo (e.g. drop Oracle references if that repo only touches PostgreSQL) — mismatched rules just add noise.
  • Instructions can also be scoped to specific paths if we want different rules per module.
  • Treat this as a living document — watch what Copilot flags or misses over the next few PRs and tighten vague rules into concrete, explicit ones.
