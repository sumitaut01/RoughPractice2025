One-line answer for the interview: SOAP is a rigid, XML-only protocol with a formal contract (WSDL) and built-in security/transactions — REST is a lightweight architectural style built on HTTP verbs and stateless resource access, which is why it dominates modern APIs and tools like RestAssured are built around it.

// The 6 constraints of a RESTful architecture (Fielding)

01

Client–Server

Client and server evolve independently. The client only needs to know the resource URI; it has no knowledge of how the server stores or processes data.

02

Statelessness

Every request carries all the information needed to process it. The server keeps no session/context between requests — that's why REST APIs scale so easily.

03

Cacheability

Responses must define themselves as cacheable or not (via headers like Cache-Control). Good caching cuts server load and improves client-perceived speed.

04

Uniform Interface

Resources are identified by URIs, manipulated through representations (JSON/XML), and accessed via standard HTTP methods — the constraint that makes REST "REST."

05

Layered System

A client can't tell whether it's talking directly to the end server or to an intermediary — load balancer, gateway, or cache — sitting in between.

06

Code on Demand optional

Servers can temporarily extend client functionality by sending executable code, e.g. client-side JavaScript. Rarely used in typical API design.

Interview follow-up to expect: "Is REST always stateless in practice?" — yes by constraint, though many real systems add session tokens/JWTs at the app layer; that's a client-carried token, not server-side session state, so it doesn't violate the constraint.
