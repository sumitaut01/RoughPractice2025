Pillar 01

Encapsulation

Bundling data (WebElements, driver, locators) with the methods that act on them, and hiding the internals behind a public interface.

Where it lives in your framework: the Page Object itself

Every Page Object you write is encapsulation in practice. The WebDriver instance and By locators are kept private; the outside world (your test class) never touches a locator directly — it only calls a public method like login() or searchProduct().

public class LoginPage {

    // state is hidden — nothing outside this class can touch the driver or locators directly
    private final WebDriver driver;
    private final By usernameField = By.id("username");
    private final By passwordField = By.id("password");
    private final By loginBtn      = By.id("loginBtn");

    public LoginPage(WebDriver driver) {
        this.driver = driver;
    }

    // public method = the only "door" into this class's behaviour
    public HomePage login(String user, String pass) {
        driver.findElement(usernameField).sendKeys(user);
        driver.findElement(passwordField).sendKeys(pass);
        driver.findElement(loginBtn).click();
        return new HomePage(driver);
    }
}
Why it matters If the login page's HTML changes tomorrow, you edit locators inside LoginPage only. Every test calling loginPage.login(user, pass) keeps working untouched — that's the entire point of encapsulation: internal change, zero external ripple.

The other place you use it daily: ThreadLocal<WebDriver>

In your parallel hybrid framework, the driver instance per thread is encapsulated behind a static utility class — no test ever new()'s a driver directly.

public class DriverManager {
    private static final ThreadLocal<WebDriver> driverThread = new ThreadLocal<>();

    private DriverManager() {} // prevents instantiation — encapsulation of construction too

    public static WebDriver getDriver() {
        return driverThread.get();
    }

    static void setDriver(WebDriver driver) {
        driverThread.set(driver);
    }
}
Pillar 02

Inheritance

Common driver setup, waits, and utility methods live once in a base class; every page/test class reuses them via extends.

BasePage → every Page Object extends it

public abstract class BasePage {
    protected WebDriver driver;
    protected WebDriverWait wait;

    public BasePage(WebDriver driver) {
        this.driver = driver;
        this.wait = new WebDriverWait(driver, Duration.ofSeconds(10));
    }

    protected void click(By locator) {
        wait.until(ExpectedConditions.elementToBeClickable(locator)).click();
    }

    protected void type(By locator, String text) {
        wait.until(ExpectedConditions.visibilityOfElementLocated(locator)).sendKeys(text);
    }
}

public class LoginPage extends BasePage {
    public LoginPage(WebDriver driver) { super(driver); }
    // click() and type() come free — no re-writing wait logic per page
}
Why it matters Every wait strategy, screenshot-on-failure hook, and re-try logic is written exactly once in BasePage/BaseTest. Fifty page classes inherit it instead of fifty copies drifting out of sync.

BaseTest → every TestNG test class extends it

public class BaseTest {
    @BeforeMethod
    public void setUp() {
        DriverManager.setDriver(new ChromeDriver());
    }

    @AfterMethod
    public void tearDown() {
        DriverManager.getDriver().quit();
    }
}

public class LoginTest extends BaseTest {
    @Test
    public void validLogin_navigatesToHome() {
        new LoginPage(DriverManager.getDriver()).login("user", "pass");
    }
}
Pillar 03

Polymorphism

Same method name, different behaviour — either by signature (overloading, compile-time) or by subclass (overriding, run-time).

Compile-time: overloaded helpers

public class ElementUtils {
    public void waitForElement(By locator) {
        waitForElement(locator, 10);
    }

    public void waitForElement(By locator, int timeoutSec) {
        new WebDriverWait(driver, Duration.ofSeconds(timeoutSec))
            .until(ExpectedConditions.visibilityOfElementLocated(locator));
    }
}

Same waitForElement name, two signatures. Callers choose the default or a custom timeout — the JVM resolves which one at compile time.

Run-time: overridden behaviour

public abstract class BasePage {
    public abstract boolean isPageLoaded();
}

public class HomePage extends BasePage {
    @Override
    public boolean isPageLoaded() {
        return driver.findElement(By.id("dashboard")).isDisplayed();
    }
}

public class CartPage extends BasePage {
    @Override
    public boolean isPageLoaded() {
        return driver.findElement(By.id("cartTotal")).isDisplayed();
    }
}

You can hold a BasePage page = new CartPage(driver) and call page.isPageLoaded() — the correct override runs based on the actual object, not the reference type.

The one that surprises people: WebDriver itself is polymorphic

WebDriver driver = new ChromeDriver();  // or FirefoxDriver(), EdgeDriver()...
driver.get("https://example.com");

You program against the WebDriver interface type, but the actual object is ChromeDriver, FirefoxDriver, or RemoteWebDriver. That's polymorphism baked into Selenium's own design — the reason your framework can run cross-browser without a single if (browser == "chrome") scattered through test logic.

Pillar 04

Abstraction

Exposing what a class does while hiding how — via interfaces, abstract classes, and frameworks like PageFactory.

PageFactory hides element-location mechanics entirely

public class LoginPage {
    @FindBy(id = "username")
    private WebElement usernameField;

    public LoginPage(WebDriver driver) {
        PageFactory.initElements(driver, this);
    }

    public void enterUsername(String user) {
        usernameField.sendKeys(user); // how it's found (lazy proxy, @FindBy) is fully abstracted away
    }
}

The test caller has no idea whether Selenium used a lazy proxy, re-located the element on every call, or cached it. That complexity is abstracted behind @FindBy + PageFactory.initElements().

ITestListener — TestNG's own abstraction for reporting hooks

public class TestListener implements ITestListener {
    @Override
    public void onTestFailure(ITestResult result) {
        ScreenshotUtil.capture(result.getName());
        ExtentReportManager.logFail(result);
    }
}

You never call onTestFailure() yourself — TestNG's engine calls it for you at the right moment. You only implement the "what happens on failure" contract; TestNG owns "when it gets triggered."

Rehearse it

Interview-style Q&A

"Where exactly have you used OOPs in your framework?" — how do I answer this in 30 seconds?

Give the one-line map, not a definition dump: "My Page Objects encapsulate locators and driver state; BasePage/BaseTest give inheritance for shared setup and waits; method overloading and isPageLoaded() overrides give polymorphism; and PageFactory plus interfaces like ITestListener abstract away the how." Then offer a concrete example if they want to dig in.

Why use Page Object Model at all — isn't that just "organizing code"?

POM is encapsulation + abstraction applied to UI automation specifically: it hides locators (encapsulation) behind readable action methods (abstraction), so a UI change means editing one page class instead of every test that touches that screen.

Overloading vs overriding — what's the one-line difference?

Overloading = same method name, different parameters, resolved at compile time (your waitForElement(locator) vs waitForElement(locator, timeout)). Overriding = subclass redefines a parent's method, resolved at run time based on the actual object (your isPageLoaded() per page).

Why is BasePage often abstract instead of a normal class?

Because it's never meant to be instantiated on its own — it only exists to be extended. Marking it abstract makes that intent explicit and lets you declare methods like isPageLoaded() that every subclass must implement, which is abstraction + inheritance working together.

How does composition fit in — do you use "has-a" relationships too?

Yes — worth mentioning if asked. A CheckoutPage often has-a HeaderComponent and has-a PaymentFormComponent as fields, rather than inheriting from them. That's composition, and it's why "favor composition over inheritance" is a natural follow-up point if the interviewer pushes further.

Any pitfall to avoid mentioning as a "best practice"?

Deep inheritance chains (Page → BasePage → BaseComponent → BaseElement...) look impressive but get brittle fast. A shallow, one-level extends BasePage plus composition for shared widgets (headers, modals) is the more defensible answer if asked about framework design trade-offs.
